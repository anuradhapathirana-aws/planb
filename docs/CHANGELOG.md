# Changelog — Plan B International

All notable changes to this project are documented here. Format loosely follows [Keep a Changelog](https://keepachangelog.com/).

## Unreleased

### Added
- **A student record now carries a CV and a 3-minute profile video.** Both are attached from the Add/Edit Student form in the admin panel and validated on both sides — PDF only, max 5MB for the CV; MP4/MOV, max 10MB for the video.
  - **Neither file ever gets a URL.** They live on a new private `student_documents` disk with no `url` configured, and `StudentResource` exposes only `{ has_file, file_name, file_size_bytes, uploaded_at }`. Viewing one costs a round trip to `/admin/students/{id}/documents/{cv|profile-video}/link`, which runs the `view` policy and returns a 30-minute signed URL. A CV is a bundle of PII — address, phone, employment history — so the reasoning that keeps lesson videos off a public disk applies with more force here, not less. The bytes are served by a route *outside* the auth group, because a `<video>` element and a PDF viewer both fetch their source without cookies; the signature is the authorization, exactly as for course video playback.
  - **Type is checked twice, by extension and by sniffed content.** `mimes:pdf` alone passes a renamed `.exe`; `mimetypes:application/pdf` alone passes a PDF named `.txt`. Both rules are present, and the media collection's own `acceptsMimeTypes` guard is a third gate — a test uploads an MP4 named `resume.pdf` and asserts it is refused.
  - **The 3 minutes is guidance, not a rule.** Reading a duration server-side needs ffprobe, which the VPS does not carry, and the browser can only report a duration it is willing to decode — so the size cap is the enforced limit and the form says "about 3 minutes, up to 10MB". A low-bitrate clip longer than three minutes will pass; the alternative was a new server dependency for a soft limit.
  - **Files are uploaded against a saved record, never inside the form post**, the same as the profile photo and for the same reason. On create the picked files are staged and go up one at a time after the student exists; a failure names which file did not make it and leaves the student saved rather than rolling back a good record over an attachment.
  - **The student's own profile screen in the mobile app is untouched.** Only admins upload these today; the endpoints are already there if that changes.
  - 16 new backend tests covering both happy paths, both size caps, type spoofing in both directions, replacement, removal, role permissions, and that the byte route refuses an unsigned request.

- **Premium Services on the student app — a fifth tab, and the whole buy-and-track loop.** The service API shipped with the admin panel; this is the phone half of it. Services sits directly after Courses in the tab bar, which takes the app to the five tabs root `CLAUDE.md` §8 caps at.
  - **Nothing about paying was rebuilt.** A service order is an order, so `useCheckout`, the hosted-checkout handoff, the bank-transfer form and the "we don't know yet" panel are reused unchanged. The checkout screen learned one thing: `item.type` is now `"course" | "service"`, and a paid service says "Plan B will start work on this" rather than "your course is unlocked" — a course opens the moment it is paid, a service is work that has not started yet, and promising otherwise is how you get a support call an hour later.
  - **A service is bought from its own screen, never from a list row** — the one place this deliberately parts company with `CourseCard`. A service is bespoke work described in rich text; buying it off a one-line summary is how a student ends up paying for something other than what they pictured, and unlike a course it cannot be un-bought. The card carries price, delivery estimate and status, and opens the service.
  - **A delivery tracker, not just a badge.** Paid → In progress → Completed with the date each step happened, plus the estimate while there is still waiting to do. The gap between paying and hearing back is real and normal for work somebody does by hand; a tracker turns it into a wait the student can *see* rather than silence they have to ask about. Cancelled **replaces** the last step rather than adding a fourth — drawing a "Completed" step that will never light up would be a lie about what is still possible.
  - **`latest_purchase` now comes down with the service itself**, scoped to the caller on the server. The detail screen draws its tracker without a second request and without cross-referencing a list the student may never have opened. A test asserts another student's purchase never appears there.
  - **A withdrawn service keeps its purchase.** "My services" loads the service `withTrashed()` — it was paid for and the work is still owed — and the new `service.is_available` flag says whether the catalogue entry still resolves, so the row stops being tappable instead of linking into a 404. `title_snapshot` carries the wording either way.
  - **Home gains one strip, and only when something is in flight.** "CV Writing · In progress", above the course catalogue because what a student is already waiting on outranks what they might browse next. It renders nothing at all when there is no open purchase, so a student who has never bought a service never sees it. It reads the same `['service-purchases']` cache the Services tab uses, so opening that tab costs no request.
  - **`has_open_purchase` is presentation, and is commented as such in three places.** It swaps a Buy button for a status line; the 422 from `POST /student/services/{id}/purchase` is what actually stops a double charge. The app sends no amount and no body, and `item.type` is a public token — never the backend's class name — so an older build seeing an unknown type shows the order and offers no shortcut rather than breaking.
  - **The description renders through the app's own allowlist parser** (`parseHtml`/`RichText`), never a WebView — the same path checklist item descriptions already take. `planb://service/<anything>` is a deep link, so a non-numeric id is treated as a failed load rather than rendering a screen with nothing on it but a back button.
  - 3 new backend tests (22 in the student service suite). Suite is now **327 tests / 1092 assertions**, all passing. Both clients type-check clean and the Android bundle builds.
  - **The new `services.*` strings are English-only** — same as the checklist and home ones, `si.json` is partial by design and Sinhala comes from the client.

- **Premium Services — a second thing students can buy, and the queue for delivering it.** Services (CV writing, visa consultation and the like) are priced, published and sold exactly like courses; what is different is what a payment produces. Two new tables (`services`, `service_purchases`), a full admin section, and the student endpoints the app will consume.
  - **The payment layer did not change, and that was the point.** `Service` implements `App\Contracts\Purchasable`, so orders, payments, webhooks, receipts, bank transfers and the PCI-SAQ-A hosted-checkout handoff all sell one without a line of change — the seam that was built for exactly this. The only edit to `PaymentService` is one `instanceof Service` branch in `settleOrder`, which previously logged "no fulfilment handler" for anything that was not a course.
  - **A course grants access; a service creates work.** `enrolments` was deliberately concrete rather than polymorphic (`docs/schema.md`), because an enrolment is access that simply exists whereas a service produces a deliverable. So `service_purchases` is its counterpart with a lifecycle an admin advances by hand — `pending → in_progress → completed`, or `cancelled` — with `completed` and `cancelled` terminal so a closed request's timestamps stay a truthful history rather than whatever was written last. The transition table lives on the enum and is enforced in the Service; the API returns `allowed_transitions` so the UI never offers an illegal move, and still 422s if one is sent.
  - **`unique(service_purchases.order_id)` is load-bearing**, the same way `enrolments.unique(student_id, course_programme_id)` is. Gateways retry until they get a 200, so the same success arrives more than once; one purchase per order makes a replay incapable of creating a second job for the delivery team. `firstOrCreate` turns the race into a no-op rather than an error.
  - **A repeat purchase is blocked while one is open, not forever.** A second visa consultation is a real thing, so a once-only unique index would have been wrong; buying again while the last is still `pending` or `in_progress` is refused, which is what stops a double tap becoming a double charge for work nobody has started. `OrderService` already reuses an unsettled order, so backing out of checkout and returning does not stack orders either.
  - **`settleOrder` now resolves the product `withTrashed()`.** Courses and services are both soft-deletable, and an admin withdrawing one between checkout and callback would otherwise resolve the morph to `null` — a student who paid, and a warning in the log instead of the thing they bought. A test covers exactly that sequence.
  - **A service may not be free.** `price_cents` must be above zero, enforced in the Form Request where the admin sees it: `OrderService` refuses to open an order for a free item, so a zero-priced service would have shipped a Buy button that silently does nothing.
  - **`services.name` is indexed but not unique, deliberately.** MySQL cannot express a partial unique index over `deleted_at IS NULL`, so a column constraint would turn "delete a service, later create one with the same name" into a 500 rather than a form error. Uniqueness is enforced in the Form Request against non-deleted rows, and a test covers the soft-delete case.
  - **Student routes take a raw `{service}` id, not a bound model.** `Route::bind` registers on the router **globally**, so a published-only binder named `service` would also rewrite the admin panel's `/admin/services/{service}` and hide every draft from the people whose job is to write them — the trap `routes/api_student.php` already documents for `course`. The published scope lives in `StudentServiceCatalogService` instead, and that scope *is* the read authorization: a draft or deleted service 404s before any controller runs.
  - **Own Resources on the student side, as always** (root `CLAUDE.md` §16.5). `admin_note` is an internal working note *about* the student and `handled_by` names staff; neither appears on `StudentServicePurchaseResource`, and a test asserts their absence rather than trusting the client not to render them. `has_open_purchase` on the catalogue is presentation only — it lets the app show "In progress" instead of a Buy button that would 422; the refusal itself is on the endpoint.
  - **Roles split along what the work actually is.** Authoring and pricing a service is content work (Super Admin / Content Manager, mirroring courses); working the delivery queue is operations (Super Admin / Support Agent). Every admin role can read both. Deleting a sellable product stays Super Admin.
  - **Admin UI follows the established patterns rather than inventing any.** Services is a compact list page with a collapsible staged `FilterCard`, `RowActions` icon buttons and a sticky action column; the form is a sectioned full page (it carries the rich-text editor, so it gets its own chunk) with the standard `ImageDropzone` and `SegmentedToggle`; the delivery queue is a list with a right-hand detail sheet, like Orders. Two new sidebar entries: **Services** under Content, **Service Purchases** under Operations. Clicking a service's purchases count deep-links into the queue already filtered.
  - **The rich-text description is sanitized server-side on write**, in `ServiceCatalogService`, through the same `HtmlSanitizer` allowlist the editor's toolbar is kept in step with. The thumbnail is re-encoded to 1280×720 JPEG via Intervention Image before storage (§7.4), matching course art so the two share one aspect ratio wherever they appear together.
  - **Search terms are LIKE-escaped.** `%` and `_` are wildcards; typed into a search box they are literals, and an unescaped `%` would return the entire catalogue. Both the student search and the two admin ones escape them, and the student OR is wrapped in its own closure so it cannot escape the `published` filter around it.
  - 37 new backend tests. Suite is now **324 tests / 1082 assertions**, all passing. Web type-checks and builds clean.
  - **Mobile screens are not in this pass.** The student API is complete and tested, so the app is UI only when it comes.

- **Course search on Home, matching course names and topic titles.** A search field above the hero banner opens a dropdown of compact result rows, filtered by three tabs.
  - **Topic titles are searchable, not just course names**, because that is where the words students actually type live — nobody searches "Course Module 3", they search "visa" or "medical". `GET /student/courses?search=` now matches either. The OR is wrapped in its own closure so it cannot escape the `status = published` filter around it; a test asserts a draft course with a matching topic never leaks.
  - **A topic match explains itself.** The response carries `matched_topic` — but only when the course's own name did *not* match — so a search for "visa" returning "Labour Law Basics" shows "Topic: Visa renewal" instead of looking like a bug. One extra query per page rather than one per row, and a course matching on both name and several topics is returned once.
  - **`%` and `_` in the search term are escaped.** They are LIKE wildcards; typed by a student they are literals, and unescaped `%` would match the entire catalogue. `like %term%` rather than a FULLTEXT index: the catalogue is dozens of rows, and FULLTEXT cannot match a partial word — "vis" finding "visa" is exactly what type-ahead needs.
  - **New column `course_programmes.published_at`** (see `docs/schema.md`). `status` is a flag with no history, so it could not answer "what is new?". Stamped on the **first** publish only and never refreshed — an admin who unpublishes to fix a lesson and republishes a week later has not created a new course. Kept out of `$fillable` so no form can backdate a course into the badge; backfilled from `created_at` rather than `updated_at`, which moves on every typo fix and would have made old courses look new.
  - **Tabs are Available · Enrolled · Unfinished.** The brief was "New (this month, not enrolled) / Enrolled / Not completed", but that leaves a hole: an older course the student has not enrolled in belongs to no tab, so searching for it would return "no results" in all three despite matching. Tab 1 became "not enrolled, any age" with `is_new` demoted to a gold NEW chip on the row — nothing falls through, and "what is new this month" is still answered. `unfinished` is a **subset** of `enrolled`, not a sibling: these are filters over one result set, not a partition.
  - **"This month" is a rolling 30 days** (`CourseProgramme::NEW_FOR_DAYS`), not the calendar month it stands in for — on the 1st, a calendar month shows an empty tab even though something shipped yesterday. One constant to change.
  - **Two data paths, one query key family.** An empty box reuses the `['courses']` response Home already fetched for its tiles and carousel, so opening the dropdown to browse costs no request at all. Typing hits the server, because matching a topic title is not something the client can do — `StudentCourseSummary` carries no topics by design. Tab filtering is always client-side, so switching tabs never costs a round trip. Input is debounced 300ms with a 2-character floor: spelling "medical" would otherwise fire eight requests, seven already stale on arrival, each billed to a student on a metered connection.
  - **The dropdown is rendered at screen root, not inside the field**, and that is load-bearing rather than stylistic: Android does not deliver touches to a child drawn outside its parent's bounds, so a scrim nested in the 48px-tall field would be invisible to every tap. The screen measures the field's bottom edge with `onLayout` and passes it down. `elevation: 8` on the panel because Android paints by elevation, not document order.
  - **New `CourseResultRow` rather than reusing `CourseCard`.** The card is ~230px tall because its 16:9 artwork is the point in a browsing list; three of them would bury the screen under a dropdown. The row shrinks the thumbnail to a 68px chip and keeps only what identifies the course — name, why it matched, and either progress or price with an Enrol button. `CourseCard` is untouched.
  - **New `SearchField` primitive**, separate from `Input` rather than a variant of it: `Input` is a form field whose always-visible label is deliberate (a placeholder-as-label strands anyone who looks away mid-entry), whereas a search box is self-evident from the magnifier and a label above it would cost a line at the top of Home for nothing.
  - 9 new backend tests. Suite is now **285 tests / 960 assertions**, all passing. Both clients type-check clean.

- **Mobile Home screen redesigned, and an admin-managed hero banner behind it.** Home answers three questions in the order a returning student asks them — who am I signed in as and what is today, how far along am I, and what do I do next — instead of opening straight onto a course card.
  - **A standard app header, pinned above the scroll**: profile photo, greeting, and a live date + time. The whole row is one tap into Profile. The clock (`src/lib/useNow.ts`) times its **first** tick to the next real minute rather than 60s from mount, so it does not flip half a minute after the phone's own status bar, and it re-reads on foreground because timers are throttled or frozen while backgrounded — coming back after lunch would otherwise show a stale time. Formatted through `Intl` with the app's locale, and explicitly **not** an accessibility live region: a screen reader announcing the time every minute over whatever the student is doing would be the most irritating thing in the app.
  - **Two progress tiles side by side** — Checklists and Courses — each a tap into its own tab. Both are computed from the *same* cached `GET /student/checklists` and `GET /student/courses` responses those tabs use, not from a Home-specific endpoint: two numbers that could disagree with the screen they link to would be worse than no numbers. The checklist tile counts **both phases as one list** (a student thinks "how much is left", not "how much of Before Arrival is left"), and the course tile counts **lessons watched across all enrolled courses** rather than averaging their percentages — averaging would let a finished two-lesson course outweigh a barely-started forty-lesson one. **There is deliberately no `/student/home` aggregate endpoint**: three parallel requests cost one round trip more, and two of them warm the tabs the tiles link to.
  - **A hero banner Plan B controls from the web panel** — the one part of the student app the client can change without a store release. New singleton table `home_banners` (see `docs/schema.md`) with the image as a Media Library collection re-encoded to 1200×600 JPEG, plus `GET|PUT /admin/home-banner` and its own image endpoints, and `GET /student/home-banner`. **A singleton, not a list**: a list would have meant a CRUD screen, an ordering UI and a "which one is live?" question, to solve a problem the client does not have.
  - **The link target is a fixed enum plus one typed column per branch**, not a free-text route: the app has to resolve each case to an `expo-router` path, and a route string typed into an admin form would be a dead end the first time navigation changed. A `course` link must name a **published** course (a draft is a 422 — the student route binds courses through a published-only scope, so they would land on a 404), a `url` link is validated `url:http,https`, and switching link type clears the branch that no longer applies so a stale course id cannot come back to life on the next switch. A course hard-deleted afterwards nulls its own foreign key and the banner **degrades to signage** rather than pointing at nothing.
  - **The student resource returns the link already resolved** — one discriminated `link` object rather than the three columns the admin resource exposes — so the client switches on a union instead of re-implementing "which column applies" (root `CLAUDE.md` §16.5).
  - **`{ "data": null }` is a normal answer**, covering nothing-set-up, switched-off, and active-with-no-image identically. The app renders its own branded fallback hero — the logo's ascending arc, drawn in SVG rather than shipping the 590KB logo PNG — so the top of Home is never an empty box. An admin banner whose image fails to load falls back the same way, because overlaid text on an empty box is worse than no banner.
  - **Overlaid wording always gets a scrim.** Admin artwork is unpredictable and a pale photo would swallow white text; the scrim guarantees legibility on whatever gets uploaded rather than hoping for a dark image.
  - **The admin screen carries a live phone-shaped preview** (Settings > Home Banner), in the app's own colours rather than the admin palette. A banner is the one piece of admin content whose entire job is how it looks on a 390px screen — editing wording and guessing at the crop from a desktop form is how you ship a headline sitting on somebody's face. It also warns when the banner is switched on but has no image, which looks saved and live from every angle except the one that matters.
  - **Course carousel cards are now a uniform width and height.** Width was already computed once so the first card lines up with the heading and the peek is identical on every phone; height now comes from the tallest card via `alignItems: 'stretch'` plus a new `fill` prop on `CourseCard` that pins the footer with `flex-1 justify-between` and reserves the category line even when a course has none. Previously a course with no category, or a one-line name beside a two-line one, left the progress bars on different lines and the row looking broken. Vertical lists are unaffected — each row still sizes to its own content.
  - 15 new backend tests. Suite is now **276 tests / 937 assertions**, all passing. Both clients type-check clean.
  - **The new `home.*` strings are English-only** — same as the checklist ones, `si.json` is partial by design and Sinhala comes from the client.

- **Arrival Checklists on mobile — the student side, end to end.** The admin has been able to author the Before Arrival / After Arrival steps for a while; students can now work through them. One new table (`student_checklist_items`), two student endpoints, and a fourth tab in the app.
  - **`student_checklist_items` keeps the row on an un-tick** and nulls `completed_at`, rather than deleting it. That makes tick and un-tick the same idempotent upsert — so a request retried on a flaky connection lands on the same answer instead of flipping the state back — and keeps the one fact worth keeping, the date a student actually finished a step. Progress stays **computed** (`COUNT(completed) / COUNT(items in phase)`), never stored: a counter would go stale the moment an admin adds a step.
  - **Both phases come down in one `GET /student/checklists`.** They are two tabs over a few dozen short rows; a request per tab would buy a spinner on every switch and save nothing on a connection where the round trip is the expensive part. `PUT /student/checklist-items/{id}` sends `{ is_completed }` — the state the student wants, not "flip it" — and answers with the item plus the phase's recounted progress, which the app's ring re-seeds from. The unique index turns a genuine double tap into a caught duplicate rather than two rows.
  - **No entitlement check, deliberately.** The checklists are Plan B's migration guidance, not purchased content, so every signed-in student sees both phases. What is scoped per student is the ticks, and they always go through the authenticated `Student`. Own resources throughout (`StudentChecklistItemResource` / `StudentChecklistPhaseResource`), never the admin ones — root `CLAUDE.md` §16.5.
  - **An HTML renderer for admin rich text, with no new dependency** (`mobile/src/lib/parseHtml.ts` + `components/shared/RichText.tsx`). Item descriptions are where Plan B writes the *steps* for a step, and they arrive as HTML that React Native cannot render. `react-native-render-html` was rejected: `App\Support\HtmlSanitizer` has already reduced every stored description to seventeen tags on write, so a general-purpose renderer would carry a hundred tags we forbid, ~200KB, and a third party between admin content and students. ~330 lines of parser + renderer covers the allowlist exactly. It assumes nothing about its input though — unknown tags unwrap, unclosed tags close, stray closers are ignored, `javascript:` hrefs render as plain text — so a description hand-edited in the database degrades to its words rather than to a crash. Verified against real TipTap output including malformed nesting.
  - **An ordered list renders as numbered gold step chips**, which is the whole reason steps are worth authoring as a list: a student sees "do 1, then 2, then 3" at a glance instead of parsing a paragraph. Gold on its own tint is also the one safe way to put the accent behind text (`tokens.ts`).
  - **Steps expand inline, not in a sheet.** The checkbox stays on screen while the student reads, so it is read-a-step-then-tick in one motion; a sheet would cover the list and make the tick a second, separate action. One item open at a time — every description unfolded is a wall of text that hides the checkboxes. The action is repeated as a button at the end of a long description, where the student finishes reading.
  - **Ticking is optimistic** and rolls back **only the failed item**, not the whole list, which would undo a tick made while the first was in flight. Out-of-order responses are dropped by comparing against the student's latest intent per item — tick-then-untick on a slow connection would otherwise flip the box back under their finger. Every failure toasts.
  - **New `Checkbox` primitive** (`components/ui/Checkbox.tsx`): a 26px circle inside a full 44×44 touchable, because a 44px circle looks like a button and a 26px touchable is the easiest control in the app to accidentally make unhittable. The fill springs in — a checklist tick is the one interaction whose entire reward is the feedback — and honours reduce-motion.
  - **Fourth tab, `ListChecks` icon.** Home / Courses / Checklists / Profile. Jobs still has no backend, so it still has no tab.
  - 9 new backend tests. Suite is now **261 tests / 879 assertions**, all passing. Both clients type-check clean.
  - **The new `checklist.*` strings are English-only** — `si.json` is deliberately partial and Sinhala comes from the client (root `CLAUDE.md` §8), so they fall back to English until translated. Send the client the new keys.

- **Student mobile app — project set up, and the student API's foundation.** The platform gains a second client: `mobile/`, React Native + Expo, one codebase for Android and iOS. Students were previously records that nobody could log in as; they are now an authenticatable actor. Three pieces landed together:

  **1. Instruction files rewritten first.** The root `CLAUDE.md` said "Web app only (PWA). No native mobile app in Phase 1", which every session was reasoning from. Rewrote §1 (two clients over one API), §2 (repo layout + the `shared/` carve-out), §3 (mobile stack), §4.12 and §13.12 (auth is now two modes; mobile tokens live in `expo-secure-store`, never `AsyncStorage` — React Native's `localStorage`), §13.5–6 (NativeWind and the RN primitive set), and §16 (rewritten from "a future React Native app will…" to what exists). Added scoped `backend/CLAUDE.md` and `mobile/CLAUDE.md`.

  **2. `shared/` — one API contract, two clients.** A source-only TypeScript package (types, Zod schemas, `serverErrors.ts`, brand tokens, EN/SI strings) with **no dependencies of its own**; both apps reach it through a `@shared/*` path alias — Vite by alias, Metro by `watchFolders`. Chosen over npm workspaces because there is nothing to install, so nothing to hoist: no root `package.json`, no workspace tooling, and Expo autolinking is left alone. `web/src/types/*` and three `lib/` helpers moved there (`git mv`, history preserved) and ~78 imports across 48 files were rewritten. `htmlToPlainText` stayed behind in `web/` — it needs `DOMParser`, which React Native has no equivalent for; `web/src/lib/formatters.ts` is now a barrel re-exporting the shared ones plus that. Note `tsconfig.app.json` maps `axios`/`zod`/`react-hook-form` explicitly: `shared/` has no `node_modules`, so Node resolution from its files walks up past the repo root and never reaches `web/node_modules`. Bundlers don't need this; `tsc` does.

  **3. Student authentication — emailed one-time code, or Sign in with Google.** No SMS and no phone verification: the client's call, and it removes the only recurring per-student cost. Two new columns (`students.email_verified_at`, `students.google_sub`) and one new table (`student_login_codes`) — see `docs/schema.md`. There is still no password column; possession of the mailbox is the credential.
  - **The guard split is the security-critical part, and Sanctum does not do it for you.** `Guard::__invoke()` loops over one **global** `sanctum.guard` key, and `SanctumServiceProvider::register()` force-defines `auth.guards.sanctum` with `provider => null` — which makes `hasValidProvider()` return true for *any* tokenable model. Giving `Student` `HasApiTokens` without addressing that hands every student's token the whole admin API. Verified by removing both mitigations and watching a student token reach `/admin/students` and die inside `StudentPolicy::viewAny(): Argument #1 ($user) must be of type App\Models\User, App\Models\Student given`. Two layers, both independently proven to matter: a real `provider` on each Sanctum guard closes the **token** path, and `admin.actor` / `student.actor` middleware closes the **session** path (which the global key makes unscopable, and which the web student area will need). `tests/Feature/GuardIsolationTest.php` proves all four directions plus the admin regression case.
  - **`Student` now extends `Foundation\Auth\User`** with `HasApiTokens` and `Notifiable`, overriding `getAuthPassword()` and the three remember-token methods since neither column exists. Media collections, soft deletes, casts and relations are untouched. `google_sub` and `email_verified_at` are kept out of `$fillable` so only the auth service can write them.
  - **Every `request-code` failure returns a byte-identical 200 and sends nothing** — unknown address, blocked, deleted. Student IDs are sequential and guessable, so a distinguishable response is an account-enumeration oracle. The Form Request deliberately has no `exists:` rule for the same reason. A test asserts the bodies match character for character. The trade-off is real and accepted: the endpoint can never explain itself, so the UI copy has to.
  - **Blocking or deleting a student revokes their tokens and voids live codes immediately**, rather than leaving a 30-day token working. `EnsureStudentIsActive` covers a token minted in the same instant.
  - **Token rotation expires the old token after a 60s grace rather than deleting it** — a hard delete 401s requests already in flight while the app refreshes.
  - Google ID tokens are verified **locally** against Google's JWKS (cached 1h) via `firebase/php-jwt`, so sign-in doesn't depend on a live call to Google; `google/apiclient` was rejected as far too large for one JWT verification. An unverified Google email is refused — anyone can put someone else's address on a Google account. A blank `GOOGLE_CLIENT_IDS` **rejects every token** rather than accepting any.
  - `StudentLoginCodeNotification` is the **first queued job in the codebase**, which makes a running `queue:work` a hard dependency of signing in at all — with no error anywhere if it isn't. Flagged in `backend/CLAUDE.md` §6; it needs a supervised worker and an alert, not a README line.
  **4. The rest of the student API — courses, the no-skip rule, assessments, profile.** Four more tables (`student_video_progress`, `student_programme_progress`, `course_paper_attempts`, `course_paper_answers`) and 14 endpoints under `/api/v1/student/`.
  - **The no-skip rule is enforced server-side**, in `CourseProgressService`, because the player's clamp is UX and a modified client (or plain `curl`) will claim anything. `max_position_seconds` is monotonic and may advance by at most `elapsed_wall_clock × 2 + 5s`; a first flush with no prior timestamp is capped at the grace window, so claiming the end of a lesson immediately buys ~5 seconds rather than the whole thing. Completion needs **two** gates — position ≥ 95% *and* accumulated playback ≥ 90% — because position alone is beatable by a client that lies slowly, whereas accumulated time makes the lie cost exactly as long as watching. Tests assert both directions: an honest watcher completes a 10-minute lesson, a position-only faker never does.
  - **The endpoint returns the server's numbers**, and the player must re-seed its clamp from them — so a tampered client snaps back on the next flush. It must also seed from `max_position_seconds` on load, never from 0, or a returning student is locked back to the start of the lesson.
  - **`Route::bind()` registers globally, not per route file.** Binding `{programme}` and `{video}` in the student routes silently applied a published-only filter to `/api/v1/admin/*` and 404'd every draft course for the admins writing them — 31 tests caught it. The student routes now use `{course}` and `{lesson}`, which are also simply the right words for that audience. Those bindings *are* the read authorization: a draft or soft-deleted programme 404s before any controller runs, so no policy is involved and the six `User`-typed policies stay untouched.
  - **`is_correct` never leaves the server on a student route.** `StudentQuestionOptionResource` omits it, and a test asserts the string is absent from the whole response body — a client that merely doesn't render the field still ships the answer key in the network tab. Grading is server-side, and `submit` verifies each `option_id` belongs to its question *and* to this paper (which is why the Form Request has no `exists:` rule — that would accept any option id in the database).
  - **Correct answers are revealed only once they can no longer help** — the student passed, or has no attempts left. Showing them after a failed attempt would make unlimited retries meaningless.
  - Attempts snapshot `pass_mark_snapshot`, `total_questions`, and question/option text, so a later paper edit cannot change a stored result or make a past attempt unreadable. Starting again mid-attempt **resumes** rather than burning a retry.
  - **`publish` now refuses a programme with no lessons, or any lesson missing a file or duration** — a behaviour change to a shipped endpoint. A durationless lesson can never reach 95% of anything, so the student could never unlock the assessment; catching it at publish beats a student discovering it. Existing draft content may need durations backfilled.
  - Student playback links last 30 minutes (vs the admin preview's 90) and carry the student id inside the signature, so the byte route re-checks the block flag at play time. Residual risk stated plainly in the docs: anyone holding the URL can play it for that window — inherent to handing a URL to a platform player, and properly fixed only by Bunny Stream token auth.

- **Course pricing, paid enrolment and payments (FR-MOB-031-037, FR-ADM-018-021).** A course can carry a price; a student enrols by paying with a card or a bank transfer. Backend and admin panel in this pass — the mobile catalogue and checkout screens follow next.
  - **Built to be extended, not just to sell courses.** `orders` is polymorphic over `App\Contracts\Purchasable`, which `CourseProgramme` implements today and a `PremiumService` will implement later. The order, payment, webhook and receipt code never learns what it is selling, so premium services will need a model and a fulfilment branch — not a second payment stack. Card gateways sit behind a `PaymentGateway` interface resolved by `PaymentGatewayManager`; adding a provider is one driver and one line.
  - **Card payments keep us at PCI-DSS SAQ-A.** Every driver hands the student to the provider's own hosted checkout, so card numbers never touch our servers or the app (FR-MOB-032). A driver that accepted a card number would break that and must never be written — stated in the interface docblock.
  - **`SandboxGateway` makes the whole path testable before PayHere credentials exist.** It contacts nobody and returns a signed URL that posts a success back through the *real* webhook route, so idempotency, amount checking and settlement are genuinely exercised in development. It refuses to run in production: a deployment without real credentials must fail at checkout, never quietly hand out free enrolments. `PayHereGateway` is written and signature-verified; switching is `PAYMENT_GATEWAY=payhere` plus the merchant id and secret.
  - **The client never decides an order is paid.** `POST /student/orders/{order}/card` returns a checkout session and leaves the order `pending`. Only a signature-verified server-to-server webhook settles it — a student who closes the browser mid-payment still gets access, and one who forges a "success" redirect does not.
  - **Replay-safe by construction.** Gateways retry until they get a 200, so the same event arrives repeatedly. Events are recorded first against a `unique(gateway, event_id)` index; a retry becomes a duplicate-key error caught and reported as `duplicate`. Settlement additionally runs under a row lock and exits early if the order is already paid, and `enrolments` has `unique(student_id, course_programme_id)`. Three independent guards, because double-charging or double-enrolling is the failure that matters most here.
  - **A webhook whose amount does not match the order is refused and the payment failed** — that is either a tampered callback or a misconfigured merchant account, and enrolling the student anyway would hide both. Signatures are compared with `hash_equals`; a timing comparison leaks the expected value one byte at a time.
  - **Bank transfer never auto-approves** (CLAUDE.md §7.10). A submission moves the order to `awaiting_verification`; an admin approves or rejects it with an optional remark the student sees, and `reviewed_by`/`reviewed_at` are recorded (FR-ADM-017/020). A rejection returns the order to `pending`, not cancelled, so the student can submit a new receipt against it (FR-MOB-035) — covered by a test that actually resubmits.
  - **The paywall is enforced server-side, not in the UI.** Courses stay browsable with their syllabus and price — students cannot buy what they cannot see — but `stream`, `progress`, `paper` and `paper/attempts` all 403 without an enrolment. The lesson `is_locked` flags are presentation only. The stream endpoint checks enrolment *before* the has-a-file check, so a non-enrolled student cannot even learn whether a lesson has a video.
  - **Free courses need no order at all**: `price_cents = 0` enrols the student the moment they ask, with `source: free`.
  - Admin: a **Price** field on the Course form (blank = free) and a Price column on the Courses list; a new **Orders & payments** page with staged filters, a verification-queue shortcut, and a right-hand detail sheet showing every payment attempt, the bank reference and the receipt, with Approve/Reject. Support Agent can read the queue but not decide on it (`OrderPolicy::review`).
  - Money is integer cents end to end (CLAUDE.md §4.11). New `formatMoney` / `toCents` / `fromCents` in `shared/` are the only places an amount becomes decimal.

Existing student suites were updated to enrol first, since free access is no longer the default. Suite is now **238 tests / 808 assertions**, all passing.

### Changed
- **Android download size — the student-facing number, not the dev build's.** A development APK is a debugging tool: it carries the dev client, all four CPU architectures, and no shrinking, which is why it measures in the hundreds of MB. A Play release is delivered from an AAB as a per-device split, so none of that reaches a student. Three real reductions on top of that, all confirmed by measurement rather than assumed:
  - **Fonts are imported per weight, not from the package root** (`app/_layout.tsx`). `@expo-google-fonts/inter` and `@expo-google-fonts/noto-sans-sinhala` have root indexes that `require()` every face the family ships — 18 and 9 respectively, 8.0 MB of TTF — and Metro bundles all of them. The app loads six. Subpath imports (`@expo-google-fonts/inter/400Regular`) are individually typed and keep about 6 MB out of the download. `useFonts` now comes from `expo-font` directly, so the root index is not pulled in at all.
  - **Three native modules nothing imported are gone**: `expo-screen-orientation`, `@react-native-community/netinfo`, `@react-native-async-storage/async-storage`. Each was shipping native libraries for four architectures. AsyncStorage in particular should never come back — root `CLAUDE.md` §13.12 forbids it for tokens, and the only mentions left in the codebase are the comments in `secureStore.ts` and `authStore.ts` explaining why it is not used.
  - **R8 and resource shrinking on release builds**, via the newly added `expo-build-properties` plugin (approved as a stack addition; it is build-time only and ships no runtime code). Debug builds are untouched. R8 works from reachability, so anything reached only by reflection can look unused to it — a release build has to be smoke-tested rather than assumed.

### Fixed
- **Edit Profile crashed with "Cannot find native module 'ExponentImagePicker'".** A native module can only reach the device inside a build, but in development the JS bundle is served live over Metro — so `expo-image-picker` and `@react-native-community/datetimepicker`, added after the installed dev client was compiled, existed in the bundle and not in the binary. Both resolve their native side at *import* time, which took the whole screen down before it rendered. Two different fixes, because the two packages are not in the same position:
  - **`@react-native-community/datetimepicker` is gone.** It was used in exactly one file, it was never in the approved stack (root `CLAUDE.md` §3), and it is the wrong control for a birth date — Android opens a calendar on *today* and expects the student to page back three hundred months. `DateField` is now a pure-JS day/month/year picker built from `Sheet` and our own primitives, so it needs no rebuild, works identically on both platforms, and puts any value one tap away. Selections snap to the nearest legal date rather than being rejected at "Done", so every state the student can see is committable. `Sheet` gained `scroll={false}` for it — a vertical list nested in a vertical list fights for the same gesture on Android.
  - **`expo-image-picker` stays, but loads lazily behind a guard** (`src/lib/imagePicker.ts`). There is no JS alternative for reading the photo library, so the photo control now explains that it needs a newer build and the other five fields on the form save normally. A store build can never be in that state — the guard exists so a stale dev client degrades instead of crashing. It is also now declared as a config plugin with Plan B's own permission wording (Apple rejects library-default usage strings, and Android needs CAMERA in the manifest).

- **The stale-dev-client guards never actually worked**, and hid a crash rather than preventing one. `src/lib/imagePicker.ts` and `src/lib/webBrowser.ts` wrapped `require('expo-image-picker' / 'expo-web-browser')` in try/catch, on the reasoning that a missing native module throws at import time. It does — but in development Metro gets there first: `guardedLoadModule` catches a module's init error, hands it to `ErrorUtils.reportFatalError` (the full-screen red "Uncaught Error"), and returns `undefined` instead of rethrowing. So the `catch` never ran, the screen was already dead, and `cached` was left `undefined` — which the availability check read back as *available*, leaving the Pay button enabled. Both guards now probe the module registry with `requireOptionalNativeModule`, which returns `null` and never triggers the import; the JS module is required only once the native side has answered. `webBrowser.ts` also names the runtime (Expo Go vs a development build) in dev when the module is missing, because the remedy differs.
- **`expo-web-browser` was in the working tree but never committed**, so every EAS build produced a dev client without the native module — the actual origin of the crash above. Along with it, eight packages had drifted behind the SDK (`expo` 57.0.16, `react-native` 0.86.2); `expo install --fix` realigned them.
