# Changelog — Plan B International

All notable changes to this project are documented here. Format loosely follows [Keep a Changelog](https://keepachangelog.com/).

## Unreleased

### Added
- **Student mobile app — project set up, and the student API's foundation.** The platform gains a second client: `mobile/`, React Native + Expo, one codebase for Android and iOS. Students were previously records that nobody could log in as; they are now an authenticatable actor. Three pieces landed together:

  **1. Instruction files rewritten first.** The root `CLAUDE.md` said "Web app only (PWA). No native mobile app in Phase 1", which every session was reasoning from. Rewrote §1 (two clients over one API), §2 (repo layout + the `shared/` carve-out), §3 (mobile stack), §4.12 and §13.12 (auth is now two modes; mobile tokens live in `expo-secure-store`, never `AsyncStorage` — React Native's `localStorage`), §13.5–6 (NativeWind and the RN primitive set), and §16 (rewritten from "a future React Native app will…" to what exists). Added scoped `backend/CLAUDE.md` and `mobile/CLAUDE.md`.

  **2. `shared/` — one API contract, two clients.** A source-only TypeScript package (types, Zod schemas, `serverErrors.ts`, brand tokens, EN/SI strings) with **no dependencies of its own**; both apps reach it through a `@shared/*` path alias — Vite by alias, Metro by `watchFolders`. Chosen over npm workspaces because there is nothing to install, so nothing to hoist: no root `package.json`, no workspace tooling, and Expo autolinking is left alone. `web/src/types/*` and three `lib/` helpers moved there (`git mv`, history preserved) and ~78 imports across 48 files were rewritten. `htmlToPlainText` stayed behind in `web/` — it needs `DOMParser`, which React Native has no equivalent for; `web/src/lib/formatters.ts` is now a barrel re-exporting the shared ones plus that. Note `tsconfig.app.json` maps `axios`/`zod`/`react-hook-form` explicitly: `shared/` has no `node_modules`, so Node resolution from its files walks up past the repo root and never reaches `web/node_modules`. Bundlers don't need this; `tsc` does.

  **3. Student authentication — emailed one-time code, or Sign in with Google.** No SMS and no phone verification: the client's call, and it removes the only recurring per-student cost. Two new columns (`students.email_verified_at`, `students.google_sub`) and one new table (`student_login_codes`) — see `docs/schema.md`. There is still no password column; possession of the mailbox is the credential.
  - **The guard split is the security-critical part, and Sanctum does not do it for you.** `Guard::__invoke()` loops over one **global** `sanctum.guard` key, and `SanctumServiceProvider::register()` force-defines `auth.guards.sanctum` with `provider => null` — which makes `hasValidProvider()` return true for *any* tokenable model. Giving `Student` `HasApiTokens` without addressing that hands every student's token the whole admin API. Verified by removing both mitigations and watching a student token reach `/admin/students` and die inside `StudentPolicy::viewAny(): Argument #1 ($user) must be of type App\Models\User, App\Models\Student given`. Two layers, both independently proven to matter: a real `provider` on each Sanctum guard closes the **token** path, and `admin.actor` / `student.actor` middleware closes the **session** path (which the global key makes unscopable, and which the web student area will need). `tests/Feature/GuardIsolationTest.php` proves all four directions plus the admin regression case.
  - **`Student` now extends `Foundation\Auth\User`** with `HasApiTokens` and `Notifiable`, overriding `getAuthPassword()` and the three remember-token methods since neither column exists. Media collections, soft deletes, casts and relations are untouched. `google_sub` and `email_verified_at` are kept out of `$fillable` so only the auth service can write them.
  - **Every `request-code` failure returns a byte-identical 200 and sends nothing** — unknown address, blocked, deleted. Student IDs are sequential and guessable, so a distinguishable response is an account-enumeration oracle. The Form Request deliberately has no `exists:` rule for the same reason. A test asserts the bodies match character for character. The trade-off is real and accepted: the endpoint can never explain itself, so the UI copy has to.
  - **Blocking or deleting a student revokes their tokens and voids live codes immediately**, rather than leaving a 30-day token working. `EnsureStudentIsActive` covers a token minted in the same instant.
  - **Token rotation expires the old token after a 60s grace rather than deleting it** — a hard delete 401s requests already in flight while the app refreshes.
  - Google ID tokens are verified **locally** against Google's JWKS (cached 1h) via `firebase/php-jwt`, so sign-in doesn't depend on a live call to Google; `google/apiclient` was rejected as far too large for one JWT verification. An unverified Google email is refused — anyone can put someone else's address on a Google account. A blank `GOOGLE_CLIENT_IDS` **rejects every token** rather than accepting any.
  - `StudentLoginCodeNotification` is the **first queued job in the codebase**, which makes a running `queue:work` a hard dependency of signing in at all — with no error anywhere if it isn't. Flagged in `backend/CLAUDE.md` §6; it needs a supervised worker and an alert, not a README line.
  **4. The rest of the student API — courses, the no-skip rule, assessments, profile.** Four more tables (`student_video_progress`, `student_programme_progress`, `course_paper_attempts`, `course_paper_answers`) and 14 endpoints under `/api/v1/student/`.
  - **The no-skip rule is enforced server-side**, in `CourseProgressService`, because the player's clamp is UX and a modified client (or plain `curl`) will claim anything. `max_position_seconds` is monotonic and may advance by at most `elapsed_wall_clock × 2 + 5s`; a first flush with no prior timestamp is capped at the grace window, so claiming the end of a lesson immediately buys ~5 seconds rather than the whole thing. Completion needs **two** gates — position ≥ 95% *and* accumulated playback ≥ 90% — because position alone is beatable by a client that lies slowly, whereas accumulated time makes the lie cost exactly as long as watching. Tests assert both directions: an honest watcher completes a 10-minute lesson, a position-only faker never does.
  - **The endpoint returns the server's numbers**, and the player must re-seed its clamp from them — so a tampered client snaps back on the next flush. It must also seed from `max_position_seconds` on load, never from 0, or a returning student is locked back to the start of the lesson.
  - **`Route::bind()` registers globally, not per route file.** Binding `{programme}` and `{video}` in the student routes silently applied a published-only filter to `/api/v1/admin/*` and 404'd every draft course for the admins writing them — 31 tests caught it. The student routes now use `{course}` and `{lesson}`, which are also simply the right words for that audience. Those bindings *are* the read authorization: a draft or soft-deleted programme 404s before any controller runs, so no policy is involved and the six `User`-typed policies stay untouched.
  - **`is_correct` never leaves the server on a student route.** `StudentQuestionOptionResource` omits it, and a test asserts the string is absent from the whole response body — a client that merely doesn't render the field still ships the answer key in the network tab. Grading is server-side, and `submit` verifies each `option_id` belongs to its question *and* to this paper (which is why the Form Request has no `exists:` rule — that would accept any option id in the database).
  - **Correct answers are revealed only once they can no longer help** — the student passed, or has no attempts left. Showing them after a failed attempt would make unlimited retries meaningless.
  - Attempts snapshot `pass_mark_snapshot`, `total_questions`, and question/option text, so a later paper edit cannot change a stored result or make a past attempt unreadable. Starting again mid-attempt **resumes** rather than burning a retry.
  - **`publish` now refuses a programme with no lessons, or any lesson missing a file or duration** — a behaviour change to a shipped endpoint. A durationless lesson can never reach 95% of anything, so the student could never unlock the assessment; catching it at publish beats a student discovering it. Existing draft content may need durations backfilled.
  - Student playback links last 30 minutes (vs the admin preview's 90) and carry the student id inside the signature, so the byte route re-checks the block flag at play time. Residual risk stated plainly in the docs: anyone holding the URL can play it for that window — inherent to handing a URL to a platform player, and properly fixed only by Bunny Stream token auth.
  - A student may edit their address, contact number, date of birth, qualification, industry/profession and languages. **Not their email** — it is the credential, so changing it needs its own verify-old-then-verify-new flow and goes through support for now — nor their name, student ID or visa status.
  - 44 more tests (`StudentCourseTest`, `StudentVideoProgressTest`, `StudentPaperTest`, `StudentProfileTest`). Suite is now **194 tests / 650 assertions**, all passing.

  - **Still to come:** the Expo app itself — scaffold and UI primitives, sign-in, the course browser and no-skip player, the assessment flow, profile and Sinhala, then EAS builds.

- **Arrival Checklists — admin authoring.** The Before Arrival / After Arrival steps students will tick off in the app. One new table (`checklist_items`) — see `docs/schema.md`.
  - **Two fixed phases, driven by a PHP enum** (`App\Enums\ChecklistPhase`: `before_arrival`, `after_arrival`) rather than an admin-managed "checklist groups" table. The client's process has exactly these two stages and the student app renders them as two fixed tabs, so a groups table would have meant a second CRUD screen maintaining data that never changes. Adding a third phase later is a migration plus one enum case.
  - **One page, two tabs** (`/admin/checklists`, `ChecklistsPage.tsx`). Each tab is its own independently-saved form, so a validation error in one can never block saving the other, and each tab carries its own **footer "+ Add checklist item"** button plus up/down reorder, Expand all / Collapse all and a per-item delete — the Q&A paper's card pattern, reused. The tab strip shows a saved-item count per phase and an "Unsaved" badge appears the moment a tab is edited.
  - **Both tabs stay mounted** (`TabsContent forceMount` + `data-[state=inactive]:hidden`). Radix unmounts an inactive tab by default, which would have silently thrown away half-finished edits the first time an admin switched tabs mid-item.
  - **Every item has a rich-text description**, through the same shared `RichTextEditor` and server-side `App\Support\HtmlSanitizer` as course topic descriptions — so a step can carry sub-steps and links, and admin HTML is never stored as received. Collapsed cards show a **plain-text excerpt** (new `htmlToPlainText` in `lib/formatters.ts`) rather than rendering the markup, which would have needed DOMPurify for a one-line preview.
  - **A phase saves whole, in one transaction** (`PUT /admin/checklists/{phase}`): rows with an `id` are updated in place, rows without are created, anything dropped is deleted, and array position becomes `sort_order` — the admin never types an order. The response is the saved list, which re-seeds the form with the new ids so a second save updates rows instead of recreating them (important once student tick-off progress references them). An id from the *other* phase is a 422, not a silent move across tabs. `{phase}` resolves by implicit enum binding, so an unknown phase 404s before the controller runs.
  - **An empty checklist is a valid save** and clears the phase — unlike a Q&A paper, "nothing to do at this stage yet" is a real state, not an error.
  - Writes are gated by `ChecklistItemPolicy::manage` (Super Admin + Content Manager); any admin role can read. `manage` is a deliberate class-level ability rather than per-row `create`/`update`/`delete`, since one request does all three.
  - **Admin authoring only.** The student-facing read/tick endpoints and a `student_checklist_items` progress table come with the student area — noted in `docs/schema.md` under Deferred. The "Checklists" sidebar item lost its "Soon" badge.
  - `newClientKey()` moved out of `features/admin/courses/courseSchema.ts` into shared `lib/clientKey.ts` — it is now used by three features, and importing it out of the Courses feature would have been a cross-feature dependency.
  - 16 new backend feature tests (`ChecklistManagementTest`) covering role gates, ordering, in-place updates, cross-phase id rejection, emptying a phase and HTML sanitization. Suite is now **120 tests / 374 assertions**, all passing.

- **Student mobile app — enrolling and paying (FR-MOB-031-036).** The other half of the payments pass: a student can now browse the catalogue, see what a course costs, and pay for it from the phone. Backend contract was already in place; this adds the screens, plus the one server-side piece a mobile client needs.
  - **Home shows only what the student owns.** The "Continue learning" hero now picks from *enrolled* courses, and their other enrolled courses sit under it in a snapping carousel with a peek of the next card. Browsing and buying moved to the Courses tab — a shop on the home screen buries the thing the student came back to finish. A student with nothing enrolled gets an empty state that points at the catalogue instead of a dead end.
  - **The Courses tab has two tabs: All courses and My courses.** An enrolled course renders as the normal progress card; one the student has not bought carries a **Locked** badge on its art, its price and an **Enrol** button, so the whole catalogue is one list rather than two experiences. Both tabs are filtered from the same request — a student has a handful of courses, so a second round trip would cost a spinner and buy nothing.
  - **One entry point, `useEnrol`, from anywhere.** The app never decides whether a course needs paying for: it calls `POST /student/courses/{course}/enrol` and the server answers with either an enrolment (free) or an order (paid). Same tap for the student either way, and the price stays on the product, on the server.
  - **A server-rendered bridge page for card checkout — the piece mobile actually needed.** PayHere expects a signed form POST, and an in-app browser can only *open a URL*. Rather than shipping the signed field set to the client to assemble (which would hand a client the payment hash), `POST /student/orders/{order}/card` now returns a `redirect_url` that is always a plain URL: for a form-POST gateway it is a short-lived **signed** page on our own server that builds the POST and submits itself. The app opens one URL and never sees a gateway field. The page is `noindex` / `no-referrer`, writes nothing, re-checks payment state (a settled payment gets 410, not a fresh checkout), and refuses a non-card payment.
  - **Checkout is `expo-web-browser`'s auth session — a Custom Tab / SFSafariViewController, never an in-app WebView.** The card form has to be the gateway's own page on its own origin with the address bar visible; hosting it inside our app would put us back in PCI scope and give the student nothing to verify. **`expo-web-browser` is the one new package in this pass**, approved for exactly this.
  - **Returning from the browser proves nothing, and the app treats it that way.** Success, cancel and dismiss all land in the same place: ask the server. The screen polls the order every 2s for 45s, unlocks on `paid`, and after that says plainly that it has no confirmation yet rather than spinning forever — a student may have paid and swiped the tab away, or forged the redirect without paying. The deep-link landing route (`planb://payment/...`) deliberately reads nothing out of the URL.
  - **Bank transfer, in the app** (FR-MOB-033/034): account details, a reference field, and a photo of the slip from camera or library at higher quality than the avatar picker uses — an admin has to read a reference off it. Submitting moves the order to "being checked" and grants nothing. A rejected transfer shows the admin's remark on the checkout screen so the student knows what to fix (FR-MOB-035).
  - **Fixed a real double-charge path found during the security pass:** a student could start a card payment while their bank transfer was still in the verification queue. Both could settle, the second would find the order already paid and return quietly, and nobody would notice until a refund was asked for. `startCardPayment` now refuses while a transfer is awaiting review; rejecting the transfer returns the order to payable.
  - **Payment history** lives behind a row in Profile rather than a fourth tab (FR-MOB-036) — students check it rarely, and it is where an abandoned payment is resumed or a rejected slip resubmitted. `StudentOrderResource` gained an `item` object naming what was bought (`{type: 'course', id}`) so the app can open it after payment; the backend's class name is mapped to a public token rather than exposed, and a test asserts `CourseProgramme` never appears in the payload.
  - `shared/` gained `types/studentOrder.ts` and `schemas/bankTransfer.ts`; `StudentCourseSummary` now carries `price_cents`, `currency`, `is_free` and `is_enrolled`, which the backend was already sending. **New EN strings under `enrol.*` and `payment.*` need Sinhala from the client** — untranslated keys fall back to English, so nothing breaks meanwhile.
  - **14 new tests** (`CheckoutHandoffTest`) covering the bridge's signature (unsigned, tampered, expired, and a valid signature re-pointed at someone else's payment), that it cannot settle anything, that a settled payment cannot reopen it, that the merchant secret appears in neither the API response nor the rendered page, and the double-charge guard. Suite is now **252 tests / 840 assertions**, all passing.

- **Course pricing, paid enrolment and payments (FR-MOB-031-037, FR-ADM-018-021).** A course can carry a price; a student enrols by paying with a card or a bank transfer. Backend and admin panel in this pass — the mobile catalogue and checkout screens follow next.
  - **Built to be extended, not just to sell courses.** `orders` is polymorphic over `App\Contracts\Purchasable`, which `CourseProgramme` implements today and a `PremiumService` will implement later. The order, payment, webhook and receipt code never learns what it is selling, so premium services will need a model and a fulfilment branch — not a second payment stack. Card gateways sit behind a `PaymentGateway` interface resolved by `PaymentGatewayManager`; adding a provider is one driver and one line.
  - **Card payments keep us at PCI-DSS SAQ-A.** Every driver hands the student to the provider's own hosted checkout, so card numbers never touch our servers or the app (FR-MOB-032). A driver that accepted a card number would break that and must never be written — stated in the interface docblock.
  - **`SandboxGateway` makes the whole path testable before PayHere credentials exist.** It contacts nobody and returns a signed URL that posts a success back through the *real* webhook route, so idempotency, amount checking and settlement are genuinely exercised in development. It refuses to run in production: a deployment without real credentials must fail at checkout, never quietly hand out free enrolments. `PayHereGateway` is written and signature-verified; switching is `PAYMENT_GATEWAY=payhere` plus the merchant id and secret.
  - **The client never decides an order is paid.** `POST /student/orders/{order}/card` returns a checkout session and leaves the order `pending`. Only a signature-verified server-to-server webhook settles it — a student who closes the browser mid-payment still gets access, and one who forges a "success" redirect does not.
  - **Replay-safe by construction.** Gateways retry until they get a 200, so the same event arrives repeatedly. Events are recorded first against a `unique(gateway, event_id)` index; a retry becomes a duplicate-key error caught and reported as `duplicate`. Settlement additionally runs under a row lock and exits early if the order is already paid, and `enrolments` has `unique(student_id, course_programme_id)`. Three independent guards, because double-charging or double-enrolling is the failure that matters most here.
  - **A webhook whose amount does not match the order is refused and the payment failed** — that is either a tampered callback or a misconfigured merchant account, and enrolling the student anyway would hide both. Signatures are compared with `hash_equals`; a timing comparison leaks the expected value one byte at a time.
  - **Bank transfer never auto-approves** (CLAUDE.md §7.10). A submission moves the order to `awaiting_verification`; an admin approves or rejects it with an optional remark the student sees, and `reviewed_by`/`reviewed_at` are recorded (FR-ADM-017/020). A rejection returns the order to `pending`, not cancelled, so the student can submit a new receipt against it (FR-MOB-035) — covered by a test that actually resubmits.
  - **The paywall is enforced server-side, not in the UI.** Courses stay browsable with their syllabus and price — students cannot buy what they cannot see — but `stream`, `progress`, `paper` and `paper/attempts` all 403 without an enrolment. The lesson `is_locked` flags are presentation only. The stream endpoint checks enrolment *before* the has-a-file check, so a non-enrolled student cannot even learn whether a lesson has a video.
  - **Free courses need no order at all**: `price_cents = 0` enrols the student the moment they ask, with `source: free`.
  - Admin: a **Price** field on the Course form (blank = free) and a Price column on the Courses list; a new **Orders & payments** page with staged filters, a verification-queue shortcut, and a right-hand detail sheet showing every payment attempt, the bank reference and the receipt, with Approve/Reject. Support Agent can read the queue but not decide on it (`OrderPolicy::review`).
  - Money is integer cents end to end (CLAUDE.md §4.11). New `formatMoney` / `toCents` / `fromCents` in `shared/` are the only places an amount becomes decimal.
  - **34 new tests** (`StudentEnrolmentPaymentTest`, `OrderManagementTest`) covering the paywall, free enrolment, order reuse, card settlement, webhook replay, amount tampering, unsigned callbacks, bank-transfer review and role gates. Existing student suites were updated to enrol first, since free access is no longer the default. Suite is now **238 tests / 808 assertions**, all passing.

- **Course thumbnails.** A course programme can now carry a cover image, uploaded on the Course form and shown to students.
  - **Optional by design** — a course saves fine without one, so no existing course is blocked, and `thumbnail_url` is `null` rather than absent. Cards fall back to a neutral branded panel; the mobile course *detail* screen simply omits the banner rather than showing a large empty box.
  - **16:9, re-encoded server-side** to 1280×720 JPEG with Intervention Image before storage (CLAUDE.md §7.4) — same treatment as student photos and lesson thumbnails, and the same ratio, so course art and lesson art match wherever they appear together. Stored in a new single-file `thumbnail` Media Library collection on `CourseProgramme`; **no migration needed**.
  - **Upload timing follows the existing pattern**: on an existing course the image uploads the moment it's picked (like the student photo); on a *new* one there is no id to attach it to yet, so the file is staged with a local preview and sent as a follow-up request once the save returns an id. A failed thumbnail reports separately and never reads as a failed save.
  - New shared `web/src/components/shared/ImageDropzone.tsx` — the click-or-drag image control described in CLAUDE.md §8, filling with the image once one exists and exposing small overlaid replace/remove buttons. It never uploads anything itself, so the caller decides between immediate and staged. Also exports `ImagePlaceholder` for list rows. (The Student form still has its own inline copy of this pattern; worth folding into the shared component next time that form is touched.)
  - Surfaced in three places: a dropzone in the Course form's details card, a 16:9 preview beside the name on the Courses list, and the student course cards + course detail hero on mobile (`expo-image`, `cachePolicy="disk"` so art isn't re-downloaded on every visit, with an `onError` fallback). `CourseCardSkeleton` gained a matching banner so the list doesn't jump when data lands.
  - Both the admin and student list queries eager-load `media`, so rendering N thumbnails stays one query rather than N.
  - 5 new backend feature tests (upload, replace, non-image rejection, role gate, removal, null-when-absent). Suite is now **204 tests / 687 assertions**, all passing.

- **Course Module — Q&A question papers (FR-ADM-008c).** An admin can pre-define all questions and answers for a course programme. Three new tables (`course_papers`, `course_questions`, `course_question_options`) — see `docs/schema.md`.
  - **One optional paper per Course Programme**, at the client's direction (the SRS put one assessment per *topic*, FR-MOB-018). Students see it after finishing every video in the programme. **A programme with no paper shows nothing at all** — there is no empty-assessment state, which is exactly the behaviour asked for. `GET .../paper` returns `data: null` rather than a 404, because "no paper" is a normal state, not an error.
  - **Questions are single-correct multiple choice, with Yes/No as the two-option case** — one build covers both, and `type` (`yes_no` | `multiple_choice`) is stored so the student UI can render Yes/No as a two-button control instead of a radio list. Switching a question to Yes/No swaps in the fixed Yes/No pair, keeping whichever side was already marked correct where that still makes sense. 2–6 answers per question.
  - **Two rules the array validation can't express are enforced in `SaveCoursePaperRequest::after()`** and mirrored in Zod so the admin sees them before saving: every question needs **exactly one** correct answer, and a Yes/No question needs exactly two. Without them a paper could be saved that is impossible to score.
  - **Its own builder page** (`/admin/courses/:id/paper`, `CoursePaperPage.tsx`) rather than more fields inside the Course form — a paper can run to dozens of questions, and it saves independently so a long paper is never lost to a course-form validation error. Paper settings sit in a sticky left card; questions fill the right two-thirds as collapsible cards with up/down reorder and Expand/Collapse all, matching the Course form's shape. Reachable from a "Q&A paper" row in the Course form's details card, a row action on the Courses list, and a new "Q&A paper" column showing question count.
  - **Rules on each paper:** pass mark (default 70%, FR-MOB-023), retry limit (blank = unlimited, FR-MOB-024), and "lock until all videos watched" (FR-MOB-021 — stored now, enforced when the student area and watch tracking exist). All questions carry equal weight, so the score is simply `correct / total`.
  - Paper instructions run through the same `RichTextEditor` and `HtmlSanitizer` as topic descriptions, so they can carry links and are never stored as received.
  - Saving upserts the whole tree in one transaction and re-seeds the form with the saved ids, so a second save updates rows instead of recreating them. Questions/answers dropped from the builder are deleted; a question `id` belonging to a *different* paper is a 422, not a silent adopt.
  - **`is_correct` is admin-only.** `CourseQuestionOptionResource` includes it because only admins read this endpoint — the student-facing paper endpoint will need its own resource that omits it, or students can read the answers out of the network tab.
  - 22 new backend feature tests (`CoursePaperManagementTest`). Suite is now **104 tests / 328 assertions**, all passing.

- **Course Module — content authoring (FR-ADM-008 / 008a / 008b).** New hierarchy **Course Category → Course Programme → Topic → Video**, agreed with the client in place of the SRS's Program → Phase → Topic wording: Appendix A's 8 phases become 8 programmes under one category, so nothing in the spec is lost, only renamed. Four new tables (`course_categories`, `course_programmes`, `course_topics`, `course_videos`) — see `docs/schema.md`.
  - **Course Categories** page (`web/src/features/admin/courseCategories/`) — standard Compact Admin Data Table, activate/deactivate instead of delete, reachable from a new expandable "Courses" sidebar group alongside "All Courses".
  - **Courses list + create/edit form.** The form is a full page rather than a dialog (`CourseFormPage.tsx`): course details sit in a sticky left card (category, programme name, summary, Draft/Published `SegmentedToggle`), and topics fill the right two-thirds. **"Add topic"** appends a collapsible topic card holding a topic name, a rich-text description and its own repeatable **"Add video"** list; topics and videos both reorder with up/down controls, and Expand all / Collapse all keeps a long course scannable.
  - **The whole tree saves in one request.** `POST/PUT /admin/course-programmes` takes programme + topics + video metadata together, inside a transaction, so a half-saved course can't exist. On edit, rows carrying an `id` are updated in place (their uploaded files survive), rows without one are created, and anything dropped from the form is deleted. A row `id` belonging to a *different* programme is a 422, not a silent duplicate.
  - **Rich-text topic descriptions with hyperlinks.** Summernote was requested but is a jQuery plugin and can't drive the DOM inside React 18, so this uses **TipTap** (`@tiptap/react`, `starter-kit`, `extension-link`, `extension-underline`) behind a new shared `components/shared/RichTextEditor.tsx` whose toolbar is built from our own shadcn buttons — no second design system in the admin panel, and the editor only offers the tags the backend will actually keep. Links are added through an inline URL bar rather than a `window.prompt`. Its chunk (112 kB gzip) is lazy-loaded with the Course form only, so no other admin page pays for it.
  - **HTML is never stored as received.** New `app/Support/HtmlSanitizer.php` re-parses every submitted description against a tag/attribute allowlist: `script`/`style`/`iframe` are dropped whole, unknown tags are unwrapped (wording kept), every attribute outside the allowlist is stripped, and only `http`/`https`/`mailto`/`tel` links survive — `javascript:` hrefs are unwrapped to plain text. `target="_blank"` links get `rel="noopener noreferrer"`. Hand-rolled rather than adding a purifier package: the editor emits a small known tag set, and an allowlist that small is easier to audit than a library's config.
  - **Admin-uploaded lesson files.** Videos are uploaded per row against `POST /admin/course-videos/{video}/file` *after* the course saves — a course can carry hundreds of megabytes, which no single form post survives. The form stages each picked file locally (same pattern as the Add-student photo, scaled up), reads its **duration straight from the file in the browser** so nobody types it by hand, then uploads them **sequentially** with a per-file progress dialog; parallel large uploads just starve each other on a typical Sri Lankan connection. A failed upload lands the admin on the edit page with everything else saved, so only the failures need retrying.
  - **Playback is signed and short-lived, never a file URL** (CLAUDE.md §7.11/§13.13). ### Changed
- **Android download size — the student-facing number, not the dev build's.** A development APK is a debugging tool: it carries the dev client, all four CPU architectures, and no shrinking, which is why it measures in the hundreds of MB. A Play release is delivered from an AAB as a per-device split, so none of that reaches a student. Three real reductions on top of that, all confirmed by measurement rather than assumed:
  - **Fonts are imported per weight, not from the package root** (`app/_layout.tsx`). `@expo-google-fonts/inter` and `@expo-google-fonts/noto-sans-sinhala` have root indexes that `require()` every face the family ships — 18 and 9 respectively, 8.0 MB of TTF — and Metro bundles all of them. The app loads six. Subpath imports (`@expo-google-fonts/inter/400Regular`) are individually typed and keep about 6 MB out of the download. `useFonts` now comes from `expo-font` directly, so the root index is not pulled in at all.
  - **Three native modules nothing imported are gone**: `expo-screen-orientation`, `@react-native-community/netinfo`, `@react-native-async-storage/async-storage`. Each was shipping native libraries for four architectures. AsyncStorage in particular should never come back — root `CLAUDE.md` §13.12 forbids it for tokens, and the only mentions left in the codebase are the comments in `secureStore.ts` and `authStore.ts` explaining why it is not used.
  - **R8 and resource shrinking on release builds**, via the newly added `expo-build-properties` plugin (approved as a stack addition; it is build-time only and ships no runtime code). Debug builds are untouched. R8 works from reachability, so anything reached only by reflection can look unused to it — a release build has to be smoke-tested rather than assumed.

### Fixed
- **Edit Profile crashed with "Cannot find native module 'ExponentImagePicker'".** A native module can only reach the device inside a build, but in development the JS bundle is served live over Metro — so `expo-image-picker` and `@react-native-community/datetimepicker`, added after the installed dev client was compiled, existed in the bundle and not in the binary. Both resolve their native side at *import* time, which took the whole screen down before it rendered. Two different fixes, because the two packages are not in the same position:
  - **`@react-native-community/datetimepicker` is gone.** It was used in exactly one file, it was never in the approved stack (root `CLAUDE.md` §3), and it is the wrong control for a birth date — Android opens a calendar on *today* and expects the student to page back three hundred months. `DateField` is now a pure-JS day/month/year picker built from `Sheet` and our own primitives, so it needs no rebuild, works identically on both platforms, and puts any value one tap away. Selections snap to the nearest legal date rather than being rejected at "Done", so every state the student can see is committable. `Sheet` gained `scroll={false}` for it — a vertical list nested in a vertical list fights for the same gesture on Android.
  - **`expo-image-picker` stays, but loads lazily behind a guard** (`src/lib/imagePicker.ts`). There is no JS alternative for reading the photo library, so the photo control now explains that it needs a newer build and the other five fields on the form save normally. A store build can never be in that state — the guard exists so a stale dev client degrades instead of crashing. It is also now declared as a config plugin with Plan B's own permission wording (Apple rejects library-default usage strings, and Android needs CAMERA in the manifest).

- **The stale-dev-client guards never actually worked**, and hid a crash rather than preventing one. `src/lib/imagePicker.ts` and `src/lib/webBrowser.ts` wrapped `require('expo-image-picker' / 'expo-web-browser')` in try/catch, on the reasoning that a missing native module throws at import time. It does — but in development Metro gets there first: `guardedLoadModule` catches a module's init error, hands it to `ErrorUtils.reportFatalError` (the full-screen red "Uncaught Error"), and returns `undefined` instead of rethrowing. So the `catch` never ran, the screen was already dead, and `cached` was left `undefined` — which the availability check read back as *available*, leaving the Pay button enabled. Both guards now probe the module registry with `requireOptionalNativeModule`, which returns `null` and never triggers the import; the JS module is required only once the native side has answered. `webBrowser.ts` also names the runtime (Expo Go vs a development build) in dev when the module is missing, because the remedy differs.
- **`expo-web-browser` was in the working tree but never committed**, so every EAS build produced a dev client without the native module — the actual origin of the crash above. Along with it, eight packages had drifted behind the SDK (`expo` 57.0.16, `react-native` 0.86.2); `expo install --fix` realigned them.
