# Changelog — Plan B International

All notable changes to this project are documented here. Format loosely follows [Keep a Changelog](https://keepachangelog.com/).

## Unreleased

### Fixed
- **A lesson video above 10MB always failed to upload**, with "Course saved, but 1 video did not upload" and the real reason only in the browser console: `has a size of 95.42 MB which is greater than the maximum allowed 10 MB`.
  - **Media Library's blanket `max_file_size` was still at its 10MB default**, far under the 512MB `UploadCourseVideoFileRequest` accepts. Validation passed the file, then `addMedia()` threw `FileIsTooBig` while storing it — so the whole 95MB was uploaded before it failed, and it failed as a 500 rather than a message. It now follows `COURSE_MAX_VIDEO_UPLOAD_MB` by default (`MEDIA_MAX_FILE_SIZE_MB` overrides it), so the two caps cannot drift apart; the real per-upload limits stay in the Form Requests, where a rejection comes back as something the admin can act on. Regression test uploads a 12MB lesson.
  - **A failed upload now says why.** The toast and the failed row in the upload dialog carry the server's 422 message ("The video must be under 512 MB.", "Upload an MP4 or MOV video.") instead of only reporting that the video did not upload — an admin retrying an unchanged file otherwise has nothing to go on.
- **Editing a course programme opened with the Course category field empty**, so an admin who only meant to change a price had to re-pick the category — and re-picking the wrong one silently refiled the course. Two causes, both in `CourseFormPage`:
  - **The category was written into the form before the category list had arrived.** The page hydrates the form the moment the course detail query resolves, but the select's options come from a second, independent query. A Radix select renders its trigger label from the matching option, so a value that lands while the list is still empty has nothing to draw and keeps showing the placeholder. Hydration now waits for both queries, and the edit page holds its `PageLoader` until both are in.
  - **The select was flipping from uncontrolled to controlled.** `value` was `undefined` until the course loaded, which Radix reads as "uncontrolled" (it warns about the switch in dev). It is now `''` — the value Radix treats as controlled-but-empty — for the whole lifetime of the field.
  - **A course sitting in a deactivated category now keeps it as an option.** The list is `is_active=1` only, so the course's own category could be missing from it entirely; the field would read empty and the next save would force a category change. The programme's own `category` (already eager-loaded by `loadTree()`) is appended when the active list does not contain it.
- **A lesson watched right through often did not mark as "watched", and the student had to watch it again.** Two independent bugs, compounding.
  - **The player was firing a progress write about once a second instead of once every 15, then losing whatever each rejected write carried.** `flush` was `useCallback(..., [report])` and `useMutation` returns a new object on every render — while `timeUpdate` re-renders the hook twice a second. So `setInterval(flush, 15_000)` was torn down and rebuilt every ~500ms and **never once fired**, and the unmount effect ran its cleanup on every render rather than on unmount, flushing (and invalidating the course queries) continuously. At roughly 60 writes a minute the player sat exactly on the `student-progress` limiter and started collecting 429s — and `flush` zeroed the pending counter *before* sending, so every rejected write erased that stretch of watching for good. `flush` is now identity-stable behind a ref, and a failed report puts its seconds back.
  - **A lesson shorter than ~100 seconds could never complete on a first viewing, by arithmetic.** `CourseProgressService::allowance()` falls back to the 5-second grace window when a progress row has no `last_seen_at`, which is always the case on the first flush — capping that write at 5 seconds of credit and discarding about 10. The 90% time gate then needs `duration − 10 ≥ 0.9 × duration`, i.e. 100 seconds or longer. `StudentCourseService::playback()` now stamps `last_seen_at` when the signed playback link is issued — the moment the student demonstrably started — so the first flush measures against a real timestamp. Stamped only when null, so a returning student's allowance is never shrunk, and a client that posts progress *without* opening the lesson is still held to the 5-second window (both covered by tests).
  - **The final flush of a lesson was dropped when under a second was pending**, which is the usual case at the end — so the position that crosses the 95% gate was sometimes never reported. `flush(force)` now sends when the high-water mark has moved past what the server last confirmed, and a `playToEnd` listener reports the player's own duration.
- **Course Details reported a total run time of zero, so the duration never rendered.** `StudentCourseDetailResource` extends `StudentCourseSummaryResource` and therefore returns `total_duration_seconds`, but `StudentCourseService::detail()` only ran `loadCount(['topics','videos'])` — never the `withSum` its sibling `list()` does. The attribute came back null, the resource coerced it to 0, and `formatCourseLength(0)` returns `''`, which the app treats as "hide this". The list screen was right and the detail screen was silently blank. `detail()` now runs the matching `loadSum`, with a test asserting a two-lesson course reports 200 seconds.
- **Uploaded images (student photos, course/service/lesson art, banners, receipts) rendered as broken boxes in both the admin panel and the mobile app.** Spatie Media Library builds a public-disk URL from `APP_URL`, so every image URL the API returned was pinned to whatever host `APP_URL` happened to name — a LAN IP that DHCP had since reassigned. Files were on disk and served fine; the host in the URL simply no longer existed.
  - **Every public asset URL now goes through `App\Support\PublicUrl::forRequest()`**, which rebuilds the URL against the host that actually made the request and leaves the path untouched. The helper already existed and was already doing this for `StudentProfileResource` and `StudentCourseVideoResource` — it was just never applied to the other nine places, which is why some images worked and most did not. Applied to `StudentResource`, `CourseProgrammeResource`, `CourseVideoResource`, `ServiceResource`, `HomeBannerResource`, `PaymentResource` and the student-facing course-summary, home-banner, payment, service-summary and service-purchase resources.
  - **`HomeBanner.link_url` is deliberately left alone** — it is an admin-entered external link, not an asset we host, and rewriting its host would break it.
  - The admin now loads images from `localhost:8001` and the phone from the machine's LAN address, from the same response, with no `APP_URL` to keep in step.

### Added
- **Sign up with Google.** Students can now create their own account from the mobile sign-in screen instead of waiting for an admin to load their record. One tap, the Google account chooser, and they are in.
  - **`POST /student/auth/google` now registers as well as signs in.** It already verified the ID token against Google's published keys and matched a student by `google_sub`, then by email; the only change is what happens when neither matches. Rather than rejecting, it creates the student — auto-allocated `PB-####`, the name Google supplied, `registered_at` and `email_verified_at` stamped, and every other column left null for the student to fill in from their profile. `is_blocked` and `imported_by` keep their defaults, which is what distinguishes a self-registered student from an imported one.
  - **Google registers; the emailed code does not, and that asymmetry is deliberate.** A Google ID token proves the caller owns a verified mailbox *before* anything is written, so there is no address to guess at. `request-code` takes a typed-in address and answers identically whether or not it matches a student — that is its anti-enumeration guarantee — and creating a record there would both destroy it and hand anyone a way to fill the table. A test asserts requesting a code for an unknown address still creates nobody.
  - **`STUDENT_GOOGLE_SIGNUP_ENABLED`** (default true) closes self-registration without a deploy, falling back to the previous sign-in-only behaviour and its "contact Plan B support" message.
  - **Student ID allocation moved to `App\Services\Student\StudentIdGenerator`**, used by both `StudentManagementService::create()` and signup. Two entry points on two guards now share one locked sequence rather than two implementations that could disagree about what "next" means. `previewNextStudentId()` delegates, so the admin create form is unchanged.
  - **The signup race is settled by the database, not by checking first.** Two taps, or two devices at once, both find no record and both insert; the unique indexes on `email` and `google_sub` pick a winner and the loser reads back the winner's row instead of failing a sign-in that should have worked. Anything that is not that race is rethrown.
  - **A new student lands on Home, not on a form.** The session response carries `is_new_student` (presentation only — nothing is authorised by it), which picks the greeting. Their profile is mostly empty and the completion ring already on Home nudges them to finish it; stopping them at a visa-status field before they have seen anything worth having is how you lose them.
  - **Mobile: "Continue with Google" above the email field** on `app/sign-in.tsx`, with the email path demoted to an outline button beneath a divider — it is the slower of the two and no longer the only way in. `useGoogleSignIn` (`src/lib/useGoogleSignIn.ts`) runs the flow in a Custom Tab / `SFSafariViewController`, never a WebView, for the same reason card checkout does: the page has to be Google's own, on Google's origin, with the address bar visible. The ID token is forwarded to the API and never inspected, trusted or stored by the app. Backing out of the chooser is silent, not an error.
  - **`GoogleButton`** is its own component rather than a `Button` variant: Google's identity guidelines require their four-colour mark unrecoloured, so it cannot inherit the Plan B palette, and the mark is an SVG path rather than the `LucideIcon` that `Button` accepts. Same 44px minimum target and `minHeight`-not-`height` rule as everything else.
  - **Three new env vars on `mobile/`** — `EXPO_PUBLIC_GOOGLE_{WEB,ANDROID,IOS}_CLIENT_ID`, surfaced through `app.config.ts`. The **web** client id is required even on a phone-only build: Android and iOS ID tokens are issued with the web client as their audience, and that audience is what the backend checks, so it must also appear in the API's `GOOGLE_CLIENT_IDS`. With none set, the button hides and the app still signs people in by emailed code rather than failing at startup.
  - **`expo-linking` and `expo-constants` are now pinned by `overrides` in `mobile/package.json`, and that pin is load-bearing.** `npx expo install expo-auth-session` pulled in a dependency on `expo-linking@~57.0.9`; npm resolved it by **upgrading the shared top-level `expo-linking@57.0.8`** — which `expo-router` uses for route resolution — and nesting a second `expo-constants@57.0.17` alongside the project's `57.0.16`. Both are native modules on the startup path, so their JS no longer matched the native code compiled into the installed development build. **The bundle loaded to 100% and the app rendered a white screen**: no red box and nothing in the logs, because the failure was in expo-router's linking layer rather than in any application code. The `"$expo-linking"` / `"$expo-constants"` override syntax pins each to whatever the project itself declares, so it stays correct as the SDK moves. Removing it, or letting a package pull a newer patch of either, reproduces the white screen.
  - **`expo-auth-session` is loaded lazily, and only when Google is actually configured** (`src/lib/googleAuth.ts`). It depends on `expo-crypto` and `expo-application`, whose entry points call `requireNativeModule(...)` at module scope — a throw, not a null, when the native module is absent from the binary, which is the case for every development build made before this change. A static import would put that throw in the startup path, where expo-router's eager `require` of everything under `app/` means it lands during bundle evaluation, before any error boundary exists. Deferred and guarded, a build with no client ids never touches the module at all, and a stale dev client logs one actionable warning and hides the button instead of failing to start. `GOOGLE_SIGN_IN_AVAILABLE` gates the `<GoogleSignInButton />` element rather than a hook call, which is what keeps the hook order inside it unconditional.
  - **Two build-config gaps fixed, both of which made a standalone or freshly-built APK unable to reach the API.** `usesCleartextTraffic` is now `true` for non-production builds (`app.config.ts`, via `expo-build-properties`) — Android has defaulted it to false since API 28, so an APK silently refused every request to the Laragon backend over `http://<lan-ip>:8001`; production stays false and is still held to HTTPS by `src/lib/env.ts`. And `EXPO_PUBLIC_API_BASE_URL` is now set in the `development` and `preview` profiles in `eas.json`: `.env` is gitignored so it never reaches EAS, and without it `app.config.ts` falls back to `http://localhost:8001`, which on a phone means the phone itself. Both were called out as known gaps in `app.config.ts`'s own comments.
  - **Google Sign-In needs a development-build rebuild before it will run** (`npm run build:dev`). `expo-crypto` and `expo-application` are native modules; no amount of JS reloading puts them in an existing binary. Until then the app runs normally with the button hidden and email sign-in unaffected.
  - Adds `expo-auth-session` and `expo-crypto`. Nine new tests cover registering, re-signing in, claiming an imported record by email, matching on `google_sub` after the student changes their Google address, signup disabled, and a blocked student.

- **The lesson player follows the phone's rotation.** Turn the phone sideways and the video goes landscape; turn it back and it returns. Nothing else in the app rotates — a card grid, a checklist and a profile form all read worse in landscape and were never designed for it.
  - **`orientation` in `app.config.ts` is now `'default'`, and portrait is a JS lock instead.** That key writes the iOS plist mask and the Android activity's `screenOrientation`, and neither can be widened at runtime — while it said `'portrait'`, every `expo-screen-orientation` call would have been a silent no-op. The declaration is widened; `app/_layout.tsx` locks `PORTRAIT_UP` on startup and `useRotationUnlocked` (`mobile/src/lib/useRotationUnlocked.ts`) releases it for the lesson route only, on focus rather than mount so the screen underneath is never left sideways. `expo-screen-orientation`'s `initialOrientation: 'PORTRAIT'` covers the moment before the bundle runs, so a phone held sideways still opens the splash upright.
  - **The player's controls now clear the horizontal safe area.** In landscape the notch is beside the screen rather than above it, so the back button and the seek bar pad by `insets.left`/`insets.right`; `px-2`/`px-4` alone would have put them under the cutout.
  - **Still no `enterFullscreen()`.** The lesson screen is already full-bleed, and expo-video re-enables its native controls — including the drag-anywhere scrubber — in fullscreen on every platform, which would undo no-skip.
  - The system rotation lock still wins: a student who has turned auto-rotate off stays in portrait, which is what they asked their phone for.
  - **`expo-screen-orientation` is a native module, so the dev client and any installed build must be rebuilt** — a JS reload will not pick it up.
- **A watched lesson is marked with a tick rather than the word "Watched".** It reads at a glance down a long syllabus and does not grow when translated into Sinhala; an unwatched row still shows its run time in the same slot. The state is still announced to screen readers — it moved onto the row's accessibility label.
- **The Plan B badge is the instructor avatar on Course Details**, in place of the "PI" initials circle. `BrandAvatar` (`mobile/src/components/shared/BrandAvatar.tsx`) renders a 192px copy of `PBLogo.PNG` — 52KB, not the original 590KB, which is far more than a 28px circle can use. The source art is a gold-ringed circle inscribed in a square with black corners, so the container is `rounded-full overflow-hidden` with `contentFit="cover"`: the corners fall entirely outside the clip. `BrandMark` keeps drawing its own SVG mark — that one sits on navy, where this badge's cream field would read as a sticker.
- **Total run time now shows under the course title, beside the rating.** The row was already built for it; the number was 0.
- **Course Details: bare banner art, video icons on watched lessons, and real faces in the learner stack.**
  - **The navy wash over the header image is gone.** The photo is now shown untinted. Legibility is bought per-label instead — each banner chip sits on its own small `foreground/55` pill (neutral slate, not navy: a navy pill would read as a leftover piece of the wash). The badges along the top already had opaque fills. `react-native-svg` is no longer imported by `CourseHero`.
  - **A watched lesson shows a video icon rather than a tick.** Locked keeps the padlock and unwatched keeps the play arrow, so the three states stay distinguishable by shape and not only by colour; the row still says "Watched" in words. The topic header circle keeps its tick — it summarises a topic, not a video.
  - **The learner stack is real photos**: the signed-in student's own first, then up to two other registered learners from the new `GET /student/learner-avatars`. Cached for 30 minutes under one key, so it is fetched once per session rather than per course, and a failure just leaves the student's own photo standing.
  - **`LearnerAvatarResource` carries `photo_url` and nothing else** — no id, no name, no initials — and the endpoint is deliberately *not* course-scoped: returning the faces of students enrolled in a particular course would tell the viewer who is taking it. Only registered, unblocked students who have a photo are returned. Six tests, one of which asserts no identifying key appears anywhere in the body.
  - **The "1.2k learners" count stays hard-coded sample data** (`courseSocialProof`), at Anuradha's request — a true count would read as "3 learners" for the first months of the roll.
- **Admins can now write a student's bio too.** `bio` joins `StoreStudentRequest` and `UpdateStudentRequest` under the same `nullable|string|max:500` rule the student's own profile endpoint uses, so there is one field and one cap rather than two that can drift.
  - **The form field is a full-width textarea at the foot of "Academic & career"** in `StudentFormDialog`, `maxLength={500}`, with a note under it saying the student can edit it too and that saving replaces what they wrote. There is one value, not an admin copy and a student copy — last write wins, and the admin is told so before they type.
  - **Clearing the box clears the field**: the submit maps `''` to `null`, matching how `email` and `highest_qualification` already behave on this form.
  - **The Student Detail profile tab shows it**, spanning both columns. `InfoRow` grew an optional `multiline` prop for it — the default `truncate` is right for a name and wrong for 500 characters of free text — plus a `className` pass-through for the column span.
  - Two new admin tests (write then clear, and the 500-character cap). `StudentResource`'s comment and the shared `Student.bio` docblock, both of which said the admin form could not set it, are corrected.
- **Profile header redesigned to a client-supplied reference, and a student `bio` to fill it.** A navy panel running behind the status bar, the photo straddling its lower edge, then name, student ID, chips and the bio.
  - **`bio` is a real field, built end to end** — a nullable `text` column on `students`, exposed on both `StudentResource` and `StudentProfileResource`, capped at 500 characters in `UpdateStudentProfileRequest`, and editable by the student on their own Edit Profile screen. **Student-writable only**: it is deliberately absent from the admin `UpdateStudentRequest`, because these are the student's own words about themselves on a record that feeds visa paperwork. Two new tests (write and clear, and the cap); suite is **352 tests / 1168 assertions**, all passing.
  - **The chips are `profession` and `industry`** — the two fields on a student that read as "what I do", which is what the reference's skill tags were for. A student with neither set gets no chip row rather than an invented one, and the line under the name is the Plan B student ID, standing in for the reference's @handle because it is the number support asks for first.
  - **No back arrow and no sign-out icon in the header**, per Anuradha: Profile is a bottom tab, so there is nothing to go back to, and sign-out stays as the deliberate two-step button at the foot of the page rather than a one-tap icon next to a photo. The title sits centred and alone.
  - **The screen no longer uses `Screen`.** That component applies the top inset to the page before any child renders, which would leave a strip of page colour above the navy. It now owns its own `ScrollView`, and the panel carries `insets.top` itself — the app already sets `StatusBar style="light"` globally, so white glyphs finally land on something dark.
  - **`Input` learned to be multiline properly.** `multiline` was already being passed to the address field and reaching `TextInput` through the spread, but the container was still `items-center min-h-[52px]`, so four lines of text sat vertically centred in a one-line box. It now switches to `items-start`, a 104px minimum and `textAlignVertical="top"`. The address field is fixed by the same change.
  - Empty bio shows a "Add a short bio" prompt that opens the edit screen — the field is new and nothing else would tell a student it exists.

- **The Services tab now uses the Courses tab's layout.** Same header rhythm, same one-per-row cards, same 94px skeletons and 16px gutter — the two tabs sit next to each other in the tab bar and had no business looking like different apps. No search field, unlike Courses: a student has a handful of services, not a catalogue worth querying.
  - **`ServiceCard` (a 230px card with 16:9 art) is replaced by `ServiceListRow`**, built to `CourseListRow`'s measurements — 68px art chip, 14px title, delivery estimate under it, price in the right rail. It still has **no Buy button**: a service is bespoke work described in rich text on its own screen, and buying it off a one-line summary is how a student ends up paying for something other than what they pictured.
  - **"My services" rows carry a 4px delivery track** where an enrolled course carries its progress ring — Paid / In progress / Completed as three segments, green for done, gold for current, red when the last one is a cancellation. The full dated tracker stays on the service screen. This trades the inline stepper `PurchasedServiceCard` used to show for a list that stays scannable; the row still answers "has anything started?" without a tap.
  - **`deliverySteps()` is now exported from `DeliveryStepper.tsx`** and drives both the full tracker and the compact track. Two copies of "which step is it on?" would disagree the first time the rules change, and the two views sit one tap apart, so a student would see it.
  - `ServiceCard.tsx`, `PurchasedServiceCard.tsx` and the now-orphaned `CourseCardSkeleton` are deleted. No new strings — the existing `services.*` keys cover it.

- **Admin: Mobile Configuration > Home Banners — manage the student app's Home carousel.** The half deferred when the carousel shipped. Plan B can now add, edit, reorder, hide and delete slides without a release.
  - **A new top-level sidebar group, "Mobile Configuration".** Home Banners moved out of Settings into it — the slides are app content, not an application setting, and the group is where the rest of the phone-facing configuration will land. Settings keeps its shape with a placeholder for the app-wide settings still to come.
  - **The singleton endpoints became a resource.** `/admin/home-banner` (show/update) is now `/admin/home-banners` with index, show, store, update, destroy, plus `reorder` and per-slide image routes. `reorder` is declared before the `apiResource` so `{home_banner}` cannot swallow it.
  - **Reorder sends the sequence, not per-row numbers.** Position in the `ids` array IS the order (root CLAUDE.md §8), applied in one transaction. A **partial or duplicated list is a 422**: renumbering only the slides sent would leave the rest colliding with them, and a duplicate would put two slides in one position. Neither is expressible per-field, so both live in the Form Request's `after()` hook. It answers with the re-ordered collection, so the client seeds from the server's sequence rather than the one its buttons optimistically drew.
  - **A new slide is saved before its image is uploaded.** Media Library needs a record with an id to attach to, so the form stages the picked file behind an object URL and sends it against the id that comes back — the same order the Course form uses for lesson videos. A failed upload does not read as a failed save: the slide is real either way and art can be added from the edit screen.
  - **The list is a gallery of 16:9 cards, not a `DataTable`.** What an admin judges here is artwork, and a 40px thumbnail in a table cell answers none of the questions they actually have; the compact-table rules exist to keep dense *text* scannable. Each card shows its carousel position, showing/hidden state, link target, and a loud warning when a slide is switched on but has neither image nor headline — live from every angle except the one that matters.
  - **Order is explicit up/down buttons, not drag-and-drop** — the same call the Course form's repeatable rows make: drag is unusable by keyboard, fiddly on a trackpad, and needs a library.
  - **The form keeps its phone-shaped live preview**, now at 16:9 with the unconditional scrim and the bottom-right page dots the app actually draws, so the crop an admin approves is the crop a student sees. It reuses the shared `ImageDropzone` rather than the hand-rolled dropzone the singleton page carried.
  - `link_type` gained **Services tab** in the admin picker, matching the enum case the app already understands.
  - Role split is unchanged and tested: any admin may look, only Super Admin and Content Manager may create, edit, reorder, delete or touch artwork. 13 backend tests cover the collection, reordering and both reorder rejections.
- **Home redesigned to a client-supplied reference: profile nudge, promo carousel, Recent courses grid.** Same data, restructured around what a student opens Home to do — see what is new, and get pointed somewhere.
  - **The banner became a carousel, and `home_banners` grew a `sort_order` instead of a second table.** The original migration said turning the singleton into a rotating set would be "a `sort_order` column and a list endpoint", and that is exactly what it was: the table was already plural and the one-row rule only ever lived in `HomeBannerService`. No data migration, no re-uploading the client's artwork, no repointing Spatie's `media.model_type` — an existing banner simply becomes slide 1. `GET /student/home-banners` replaces the singular route and answers an ordered list; the admin's single-banner screen still edits the first slide and is untouched until its carousel replacement lands.
  - **A slide that is switched off, or active with no image, is dropped from the list rather than sent.** One blank page inside a swipeable carousel reads as a broken app, where a missing one reads as nothing at all.
  - **Slides peek.** The centred slide is inset 28px from each screen edge, leaving a 16px sliver of its neighbours visible either side — the cue that tells a student there is more to swipe to, since dots alone are easy to miss and a full-width slide reads as a static banner. Snapping is `snapToInterval` on the slide's own stride, **not** `pagingEnabled`, which snaps by screen width and would drift further out of alignment at every stop.
  - **Two built-in slides render when the admin has published none** — Courses and Services, the destinations the client asked for. A new install has to look finished on first launch, and a blank slot at the top of Home is the worst possible first impression. They step aside entirely the moment a real slide is published. Drawn with `react-native-svg`, not bitmapped, for the same reason as `BrandMark`.
  - **`HomeBannerLink` gained a `services` case**, so a slide can point at the Services tab. `Rule::in(HomeBannerLink::values())` picked it up with no change to the Form Request.
  - **Every title variant is Plan B navy.** `display`, `title` and `heading` moved from slate `foreground` to `primary` in the shared `Text` primitive, so it lands app-wide in one edit. `body` and below stay `foreground` — a whole screen set in brand colour stops the headings standing out at all. Checked first that no title variant sits on a navy `bg-surface` card: those set their own `text-white` on a plain `Text` and always have.
  - **`ProgressRing` gained a `tone`.** Gold stays the default and the signature; `primary` draws the arc in navy. They must not be combined with `onDark` — navy on navy is invisible, which is the case gold exists for.
  - **A profile-completion ring, computed in the app.** Nine editable fields, equally weighted, off the `StudentProfile` already in the store — no request, and the number moves the instant a student saves. Name and email are excluded deliberately: both are set at registration and neither is editable in the app, so counting them would inflate every score by a fixed amount. The card **removes itself at 100%** rather than switching to a congratulation; a permanent "well done" is dead space at the top of the most-opened screen. `useProfileCompletion` and the Edit Profile form have to stay in step — that trade is documented at the top of the hook.
  - The card is a ring, a title and a button — no body copy. It is a plain `Card` holding a real `Button`, **not** a `PressableCard`: two nested tap targets with one outcome is ambiguous to a screen reader, which announces the card and the button as separate controls doing the same thing. Its ring is navy rather than gold, because a gold arc beside a navy button read as an award for something the student has not finished yet. The `remaining` count and its two plural strings went with the body copy.
  - **"Recent courses" is a 2-up grid of `CourseGridCard`**, a new narrow sibling of `CourseCard`, carrying art, title, a star rating and a price. **No progress bar, even on an enrolled course** — these tiles are a browsing surface answering "what could I learn?", and a half-filled bar made that compete with "how far am I?", which is Profile's question; the Locked badge still marks what is not owned. **No enrol button either** — at tile width it would be a ~70px target beside a price, which is how students buy the wrong course. Sorted by `published_at`, newest first, capped at four.
  - **The Courses tab uses the same tile, two to a row**, keeping its All/My-courses toggle and its search field. Enrolling from the list went with the change, for the tap-target reason above.
  - **The tile's rating is SAMPLE DATA from the existing `courseSocialProof`**, not a second fake source — so a course shows the same stars on its tile and on its detail screen, and both disappear together when the real fields ship.
  - **A slide no longer needs artwork to go live.** `isPublishable()` now accepts wording alone, and the app draws a branded house-colours card for it — the same one the built-in slides use. - **Course pricing, paid enrolment and payments (FR-MOB-031-037, FR-ADM-018-021).** A course can carry a price; a student enrols by paying with a card or a bank transfer. Backend and admin panel in this pass — the mobile catalogue and checkout screens follow next.

Crossed orientations are fine, and they buy the virtualisation — only the tiles on screen mount, where the grid mounted all ten.
    - **This changes render cost, not fetch cost**, and that was a deliberate call: `fetchCourses` still returns the catalogue in one request because Home shares that `['courses']` response with `/browse/courses` and the Courses tab, so a Home-specific page size would either shrink theirs or need a second query key to keep in step.
    - **The break-out margin is on a wrapper, never on the list** — the trap `HomeCarousel` already documents. Both give the list full screen width, but with the margin on the list itself it is wider than its own parent, and a child overflowing its parent is what Android is entitled to clip, peek included. `removeClippedSubviews` is forced off for the same reason it is in the banner carousel.
    - **No dots.** Ten of them under a strip would be a row of noise, and the "show me the rest" affordance is the View all link already in the heading. Snapping deliberately omits `disableIntervalMomentum` too: capping a swipe at one tile suits a banner carousel and feels sluggish on a ten-item strip.
  - **The tiles carry no price and no buy button on Home**, at the client's request — a new `showPurchase` prop on `CourseGridCard`, on by default and off only here. Home is a browsing surface, so a tap opens the course and buying happens on its own screen; `/browse/courses` is the shop window and keeps both. A prop rather than a second component: the two tiles are otherwise identical, and a copy would have to be kept in step with every future change to artwork, rating, badge or layout.
    - **The price leaves the accessibility label with it.** Announcing a price a sighted student cannot see would describe a different card than the one on screen.
    - **The locked marker on a tile is now the padlock alone, no "Locked" wording.** Every tile `CourseGridCard` draws is a course the student does not own — Home's Explore strip and `/browse/courses` both filter to exactly that — so the word appeared on every tile in the grid and told nobody anything, while costing the artwork its width. The `Badge` primitive is untouched: it always renders its label, and making that optional would have changed every badge in the app for one case. The card's accessibility label still says "Locked", so nothing is lost to a screen reader.
    - **`useEnrol` came off Home entirely.** With no buy button there is nothing to trigger it, and leaving the hook wired would have kept a mutation alive that no control could reach. It still backs `/browse/courses` and Course Details.
  - **The Explore section inherited loading, error and empty**, all of which the deleted block used to own — the old strip rendered `null` on empty, which was survivable under a catalogue and is not when it is the only content. The loading skeleton is two rows rather than one, so the grid does not pop from a quarter height to full on arrival.
  - **`CourseResultRow` was deleted.** Home was its only consumer, so the change orphaned it (root `CLAUDE.md` §5). `CourseGridCard` and `CourseListRow` are untouched, and `CategoryTabs` stays — `/browse/courses` still uses it.
  - **`home.recentTitle`, `home.categoryEmptyTitle` and `home.categoryEmptyBody` are gone**, the last two having had no consumer outside Home (`/browse/courses` carries its own `browse.categoryEmpty*`). New key `home.exploreTitle`; `home.categoryAll` stays because the chip strip still reads it. `si.json` has no `home` block at all, so the new string falls back to English until the client supplies Sinhala — unchanged from the standing rule.
  - Home's page-gutter comment named four places coupled to the 10px value; `CategoryTabs` is no longer one of them *on this screen*, so it names two and says where the third moved.
- **The Services tab became My Services, the same way the Courses tab did.** Both tabs now show only what the student has, and both catalogues live behind a "+ Browse" button. The two screens were already built to match each other; keeping them in step was the point.
  - **The tab lists purchases only**, as the existing `PurchasedServiceRow` with its status badge and delivery track. The All / My-services toggle went, and the catalogue with it.
  - **`/browse/services` is the new All Services screen**, with a search field and `ServiceGridCard` tiles — a new sibling of `CourseGridCard`, same 4:3 artwork, same scrim, same type sizes. The delivery estimate rides on the artwork where a course tile puts its category, because "how long will this take?" is the first question anyone asks about bespoke work.
  - **Still no Buy button on a service tile**, which is where it parts company with the course tile. A service is bespoke work described in rich text on its own screen; buying it off a tile is how a student ends up paying for something other than what they pictured, and unlike a course it cannot be un-bought. `ServiceListRow` — the old catalogue row, which carried the same rule — is gone with the tab that used it.
  - **No category chips**, unlike the courses sibling: services have no categories. Search is client-side on both service screens, because `/student/services` takes no search parameter and the whole (short) catalogue is already in hand — a course search hits the server only because it has to match topic titles, which have no equivalent here. Each search box hides itself below two items rather than filtering a single row.
  - **The course browse screen moved to `/browse/courses`** so the two sit together, and **Home's promo slides now open the catalogues rather than the tabs**. A slide is an advert — "Find your course", "Let us handle the paperwork" — and after this change landing on a tab would answer it with "Nothing bought yet". Same fix for the service screen's dead-link fallback.

- **The Courses tab became My Courses, and the catalogue moved to its own screen.** Two client-requested changes in one pass: the tab's layout was redrawn from a supplied reference, then the All/My-courses toggle was cut entirely. One tab, one question.
  - **The Courses tab lists enrolled courses only, as full-width rows.** `CourseListRow` replaces the two-up `CourseGridCard` grid here: artwork chip, title, run time, and the progress ring on the right. A ring per row answers "how far am I?" at a glance, where a tile grid made the student read two columns of artwork to find it. It shows run time rather than topic and lesson counts — matching the reference's "Duration 2h 45m" — and falls back to the lesson count when no lesson carries a duration, rather than printing "Duration 0m".
  - **The row carries no price and no buy button**, because nothing unowned reaches this list. The toggle's removal made that branch unreachable, so it went rather than sitting there as dead code — the component is now documented as taking an enrolled course.
  - **`/browse` is the new All Courses screen** — everything the student has *not* enrolled in, as `CourseGridCard` tiles with search and the category chips Home already uses. Tiles, not rows: nothing here has progress, so the right rail a ring would occupy is better spent on artwork, and artwork is what sells a course. It is a pushed screen rather than a sixth tab, which the five-tab cap (root CLAUDE.md §8) has no room for.
  - **Four ways in**, so the catalogue is never more than a tap away: Home's "View all" beside Recent courses, a new "View all" on Home's lower Courses section, a Browse button in the My Courses header, and the My Courses empty state.
  - **The tab's search field now filters the enrolled list in place**, client-side. A student owns a handful of courses and they are all already in hand, so a request per keystroke would buy a spinner and nothing else. It hides itself below two courses — a search box over one row is dead UI.
  - **`useCourseSearch` and `CourseSearchResults` were replaced by `useBrowseCourses`.** The old hook carried Available/Enrolled/Unfinished tabs for a dropdown overlay the Courses tab opened; the enrolled halves of that live on the tab itself now, so the new hook knows one filter — not enrolled. It keeps both data paths that mattered: the warm `['courses']` cache for an empty box, and the server search for a typed query, which is the only way to match a *topic* title (`StudentCourseSummary` carries no topics, by design). `CourseSearchTab` went from `@shared/types`, and the per-tab i18n strings with it.
  - **The browse screen says what it leaves out** in a subtitle. Without it, searching there for a course you already own and getting nothing back reads as broken search rather than as "you have that one".
  - The reference's avatar/greeting header and its filter button were **not** adopted: the header belongs to Home and repeating it costs the list ~60px above the fold, and the category chips do the filtering a sliders button would duplicate.
- **Android download size — the student-facing number, not the dev build's.** A development APK is a debugging tool: it carries the dev client, all four CPU architectures, and no shrinking, which is why it measures in the hundreds of MB. A Play release is delivered from an AAB as a per-device split, so none of that reaches a student. Three real reductions on top of that, all confirmed by measurement rather than assumed:
  - **Fonts are imported per weight, not from the package root** (`app/_layout.tsx`). `@expo-google-fonts/inter` and `@expo-google-fonts/noto-sans-sinhala` have root indexes that `require()` every face the family ships — 18 and 9 respectively, 8.0 MB of TTF — and Metro bundles all of them. The app loads six. Subpath imports (`@expo-google-fonts/inter/400Regular`) are individually typed and keep about 6 MB out of the download. `useFonts` now comes from `expo-font` directly, so the root index is not pulled in at all.
  - **Three native modules nothing imported are gone**: `expo-screen-orientation`, `@react-native-community/netinfo`, `@react-native-async-storage/async-storage`. Each was shipping native libraries for four architectures. AsyncStorage in particular should never come back — root `CLAUDE.md` §13.12 forbids it for tokens, and the only mentions left in the codebase are the comments in `secureStore.ts` and `authStore.ts` explaining why it is not used.
  - **R8 and resource shrinking on release builds**, via the newly added `expo-build-properties` plugin (approved as a stack addition; it is build-time only and ships no runtime code). Debug builds are untouched. R8 works from reachability, so anything reached only by reflection can look unused to it — a release build has to be smoke-tested rather than assumed.

### Fixed
- **Edit Profile crashed with "Cannot find native module 'ExponentImagePicker'".** A native module can only reach the device inside a build, but in development the JS bundle is served live over Metro — so `expo-image-picker` and `@react-native-community/datetimepicker`, added after the installed dev client was compiled, existed in the bundle and not in the binary. Both resolve their native side at *import* time, which took the whole screen down before it rendered. Two different fixes, because the two packages are not in the same position:
  - **`@react-native-community/datetimepicker` is gone.** It was used in exactly one file, it was never in the approved stack (root `CLAUDE.md` §3), and it is the wrong control for a birth date — Android opens a calendar on *today* and expects the student to page back three hundred months. `DateField` is now a pure-JS day/month/year picker built from `Sheet` and our own primitives, so it needs no rebuild, works identically on both platforms, and puts any value one tap away. Selections snap to the nearest legal date rather than being rejected at "Done", so every state the student can see is committable. `Sheet` gained `scroll={false}` for it — a vertical list nested in a vertical list fights for the same gesture on Android.
  - **`expo-image-picker` stays, but loads lazily behind a guard** (`src/lib/imagePicker.ts`). There is no JS alternative for reading the photo library, so the photo control now explains that it needs a newer build and the other five fields on the form save normally. A store build can never be in that state — the guard exists so a stale dev client degrades instead of crashing. It is also now declared as a config plugin with Plan B's own permission wording (Apple rejects library-default usage strings, and Android needs CAMERA in the manifest).

- **The stale-dev-client guards never actually worked**, and hid a crash rather than preventing one. `src/lib/imagePicker.ts` and `src/lib/webBrowser.ts` wrapped `require('expo-image-picker' / 'expo-web-browser')` in try/catch, on the reasoning that a missing native module throws at import time. It does — but in development Metro gets there first: `guardedLoadModule` catches a module's init error, hands it to `ErrorUtils.reportFatalError` (the full-screen red "Uncaught Error"), and returns `undefined` instead of rethrowing. So the `catch` never ran, the screen was already dead, and `cached` was left `undefined` — which the availability check read back as *available*, leaving the Pay button enabled. Both guards now probe the module registry with `requireOptionalNativeModule`, which returns `null` and never triggers the import; the JS module is required only once the native side has answered. `webBrowser.ts` also names the runtime (Expo Go vs a development build) in dev when the module is missing, because the remedy differs.
- **`expo-web-browser` was in the working tree but never committed**, so every EAS build produced a dev client without the native module — the actual origin of the crash above. Along with it, eight packages had drifted behind the SDK (`expo` 57.0.16, `react-native` 0.86.2); `expo install --fix` realigned them.

### Notes / follow-ups
- **PayHere merchant credentials are still needed to take a real card payment.** Until `PAYHERE_MERCHANT_ID` / `PAYHERE_MERCHANT_SECRET` are set, `PAYMENT_GATEWAY=sandbox` is in force and settles payments locally. The sandbox refuses to run in production.
- **Mobile checkout is the next pass**: course catalogue with prices, the enrol button, card hand-off, the bank-transfer form and transaction history. The backend contract for all of it exists and is tested.
- **Refunds are not built.** `OrderStatus::Refunded` and `EnrolmentService::revoke()` exist as the seam, but reversing money needs its own flow and audit trail.
- **Receipts (FR-MOB-037)** — in-app view and downloadable PDF — are not built yet.
- **Revenue only reaches an accounts module when one exists** (FR-ACC-002/003). `GET /admin/orders/stats` reports monthly revenue today; nothing writes income records.
- **Shuffling question order on retry (FR-MOB-024) is not implemented** — it was deselected when the paper rules were agreed. Questions are always served in `sort_order`. It's a one-line change in the student-facing endpoint whenever it's wanted.
- Student-side paper attempts, scoring and progress tracking (FR-MOB-020/024/025/027), the no-skip player, and a student-facing paper resource that omits `is_correct` all need the student area, which doesn't exist yet.
- A topic can currently be saved with zero videos (the form only warns), so a course can be published without lessons. Add a publish-time check once assessments define what "complete" means for a topic.
- PWA icons (`web/public/icons/`) are placeholders — the full-resolution brand logo copied to all three required sizes. Generate properly optimized 192/512/maskable PNGs before shipping.
- `RequireRole` (per CLAUDE.md §4 Web rule 12) isn't built yet — only `RequireAuth` exists, since there's no student-facing area yet to separate from admin. Add it when the student mobile-web area or role-gated admin sections arrive.
- Zod pinned to `3.23.8` (not latest 3.25.x) and TypeScript to `^5.9` (not the auto-installed 6.0 prerelease) — both for ecosystem compatibility with `@hookform/resolvers` v3 and general tooling stability.
- Queues use the `database` driver locally (not Redis) — Redis isn't running in this dev environment. CSV import runs synchronously (bounded, with per-row validation feedback needed immediately); switch to Redis + queued jobs per CLAUDE.md before production.
- Fixed during browser verification: several hand-authored `ui/` primitives (`Input`, `Textarea`, `Button`, `Dialog`/`Sheet`/`AlertDialog` Overlay+Content, `DropdownMenuContent`, `SelectContent`) weren't forwarding refs, which silently broke every React Hook Form field (login, student form) and any `asChild`-based trigger. All now use `React.forwardRef` — required because the project is pinned to React 18, which (unlike React 19) doesn't accept `ref` as a plain prop on function components.
